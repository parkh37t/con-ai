# S2B BFF / PROCESS / PROGRAM / 명명 관리 규칙

작성일: 2026-05-27

이 문서는 `명명규칙.md`의 도메인/패키지/레이어/클래스/URL 명명 규칙을 병합한 기준 문서다.  
다른 섹션의 URL 예시나 Endpoint 예시가 `명명규칙.md`와 충돌하면 `명명규칙.md` 기준을 따른다.

## 1. 기본 전제

이 관리대장은 화면, BFF, API, 프로그램을 억지로 1:1로 묶지 않는다.

- BFF는 단독으로 존재할 수 있다.
- 프로세스는 단독으로 존재할 수 있다.
- 프로그램은 단독으로 존재할 수 있다.
- 프로세스는 BFF에 사용될 수 있다.
- 프로세스는 BFF 없이도 존재할 수 있으므로 프로세스 시트의 `BFF ID`는 선택값이다.
- 프로그램은 프로세스에 의해 사용된다.
- 프로그램은 여러 프로세스에서 재사용될 수 있다.
- 관계는 마스터 시트에 박아 넣지 않고 매핑 시트에서 표현한다.

### 2.1 ID 채번 규칙

ID는 사용자가 직접 입력하지 않고 원천 값과 순서 기준으로 자동 계산한다.

| 구분 | 형식 | 채번 기준 |
|---|---|---|
| BFF ID | `BFFPS_IM` + 4자리 | TO-BE 대상 행 순서대로 자동 채번 |
| 프로세스ID | `PS_IM`, `PS_DP`, `PS_SC` + 4자리 | `14_PROCESS_MASTER`의 `업무영역` 선택값 기준으로 자동 채번. `물품`은 `IM`, `전시`는 `DP`, `검색`은 `SC`를 사용 |
| 프로그램ID | `PG_IM` + 4자리 | 포탈별 채번 대역과 화면 순서 기준 자동 채번 |

프로그램ID 채번 대역은 아래 기준을 따른다.

| 포탈 | 채번 대역 | 첫 채번 예시 |
|---|---:|---|
| 수요기관 포탈 | 1000번대 | `PG_IM1001` |
| 공급업체 포탈 | 2000번대 | `PG_IM2001` |
| 관리자 포탈 | 3000번대 | `PG_IM3001` |

프로그램ID는 화면ID 1개당 1개를 부여한다.

## 3. `02_RAW` 규칙
`02_RAW`는 원천 확인용이다. 생성 보조 컬럼은 운영 시트에 남기지 않는다.

- 같은 S2B2 폴더의 `개발목록_TO-BE_정보구조.xlsx`를 원천으로 참조한다.
- 원천 파일명은 NFC 정규화된 한글 파일명을 유지하고, 임의로 변경하지 않는다.
- 원천 파일을 다른 폴더로 이동하지 않는다. 이동이 필요하면 관리대장과 원천 파일을 함께 이동한 뒤 링크를 갱신한다.
- 원천 포털 시트의 보조열(예: AB열)은 삭제하거나 이동하지 않는다. 행을 추가해야 하면 보조열 수식도 같은 범위까지 확장한다.
- `02_RAW`의 기본 표시 범위는 `A1:T1001`로 유지하고, 행 수를 확장할 때 원천 수식도 같은 끝 행까지 확장한다.
- 동적 배열/집계형 외부참조 수식(`FILTER`, `VSTACK`, `AGGREGATE` 등) 대신 `COUNT`, `MATCH`, `INDEX` 계열의 보수적 수식을 사용한다.
- 외부 연결 경고가 뜨면 같은 S2B2 폴더의 신뢰 가능한 원천 파일인지 확인한 뒤 업데이트를 허용한다.

## 8. BFF 1개가 여러 API/프로세스로 나뉘는 기준

한 화면 또는 한 BFF에서 API가 여러 개 필요한지는 화면 수가 아니라 업무 책임과 호출 단위로 판단한다.

API/프로세스를 분리하는 기준은 아래와 같다.

- 조회와 저장처럼 CRUD 성격이 다르다.
- 목록 조회와 상세 조회처럼 데이터 범위가 다르다.
- 팝업, 탭, 첨부, 엑셀 업로드처럼 독립 호출 타이밍이 있다.
- 권한, 보안, 인증 조건이 다르다.
- 캐싱 가능 여부가 다르다.
- 트랜잭션 경계가 다르다.
- 실패해도 화면 전체가 실패하면 안 되는 독립 기능이다.
- 다른 화면에서도 재사용할 공통 기능이다.
- 호출 Method가 다르다.

반대로 아래 경우는 굳이 API를 쪼개지 않는다.

- 항상 동시에 조회된다.
- 같은 권한과 같은 데이터 소스를 쓴다.
- 같은 화면 초기 진입에서 하나의 응답으로 받는 것이 자연스럽다.
- 분리해도 재사용성이 없고 호출 수만 늘어난다.

## 9. 화면 조회 1개에 조회 API가 여러 개 쓰이는 경우

가능하다. 다만 무조건 나누지 않는다.

| 상황 | 판단 |
|---|---|
| 화면 초기 진입에 항상 필요한 데이터 | 하나의 BFF 조회로 묶는 쪽 우선 |
| 탭을 눌렀을 때만 필요한 데이터 | 별도 조회 API 가능 |
| 팝업에서만 필요한 데이터 | 별도 조회 API 가능 |
| 권한이 다른 데이터 | 별도 API 우선 |
| 느린 통계/집계 데이터 | 별도 API 가능 |
| 공통 코드/카테고리처럼 재사용되는 데이터 | 공통 API 가능 |

BFF는 화면 요구사항을 받아 여러 API를 조합할 수 있다. 단, API MASTER나 PROCESS MASTER에는 그 조합 관계를 억지로 한 행에 넣지 않는다.



## 10. URL/URI 공통 명명 규칙

URL/URI 명명 규칙은 `명명규칙.md`를 우선한다.

### 10.1 Domain / Subdomain 세그먼트

URL의 `{domain}`은 우리 파트 기준으로 `catalog`를 고정 사용한다.

`{subdomain}`은 원본 `02_RAW`의 WBS 1~4 depth를 기준으로 아래 값을 자동 산출한다.

| 구분 | subdomain | 판정 기준 |
|---|---|
| 물품 | `goods` | WBS 1~4 depth가 물품/상품/견적/카탈로그/분류/인증/옵션/이미지 성격 |
| 전시 | `display` | WBS 1~4 depth가 전시/기획전/미니샵/몰/코너/템플릿/매장 성격 |
| 검색 | `search` | WBS 1~4 depth가 검색 엔진, 통합검색, 검색어, 금칙어, 동의어, 신조어, 추천 검색어, 검색 가중치 성격 |

WBS 1~4 depth 중 빈 값은 같은 WBS 계층의 상위 depth 값을 따른다.  
단, WBS 대분류가 바뀌면 이전 대분류의 depth 값을 그대로 끌고 오지 않는다.

### 10.2 포탈 세그먼트

URL의 `{시스템}` 또는 포탈 구분 세그먼트는 아래 값을 사용한다.

| 포탈 | 세그먼트 |
|---|---|
| 수요기관 포탈 | `buy` |
| 공급업체 포탈 | `sell` |
| 관리자 포탈 | `admin` |

### 10.3 업무구분 세그먼트

업무구분을 URL 경로에 반영해야 할 때는 아래 값을 사용한다.

| 업무구분 | 세그먼트 |
|---|---|
| 공통 | `common` |
| 이용자관리 | `user` |
| 계약접수 | `contract` |
| 물품관리 | `catalog` |
| 리포팅 및 통계 | `report` |
| 알림 및 커뮤니케이션 | `notification` |
| 기타 | `misc` |

### 10.4 하위패키지 세그먼트

BFF/API URL의 `{package}` 세그먼트는 아래 값을 사용한다.

| 하위패키지 | 세그먼트 |
|---|---|
| 물품 | `goods` |
| 전시 | `display` |

### 10.5 공통 URI 규칙

| 항목 | 규칙 | 예시 |
|---|---|---|
| 문자 | URI에는 영문 소문자, 숫자, 하이픈, camelCase Model명을 사용한다. | `/api/catalog/goods/user/search` |
| 한글 | URI에는 한글을 쓰지 않는다. | `견적조회` 금지 |
| 언더바 | `_`는 사용하지 않는다. 화면ID에 `_`가 있으면 URL에서는 `/`로 분리한다. | `sell_receipt_prespecS2BList` 금지 |
| 마지막 슬래시 | URI 마지막에 `/`를 붙이지 않는다. | `/api/catalog/goods/user/search` |
| Action | 마지막 세그먼트는 동사형 Action을 사용한다. | `search`, `find`, `create`, `update`, `delete`, `process` |
| Model | API URL의 `{Model}`은 단수형 lower camelCase를 사용한다. | `user`, `contractCategory` |

기존의 `모든 URI세그먼트는 kebab-case` 규칙은 폐기한다.  
BFF 화면ID와 API Model명에는 명명규칙 기준의 camelCase를 사용할 수 있다.

## 11. BFF URL 규칙

BFF URL은 화면 진입과 화면 전용 JSON API에 사용한다. Model 기준이 아니라 화면ID 기준이다.

| 구분 | 규칙 |
|---|---|
| 패턴 | `/{domain}/{subdomain}/{system}/{package}/{screenID}/{action}` |
| 기준 | `{domain}`은 `catalog` 고정, `{subdomain}`은 WBS 1~4 depth 기준 `goods`, `display`, `search` 중 하나를 사용한다. BFF prefix는 사용하지 않는다. 화면ID에 포함된 시스템/패키지/ID를 URL 세그먼트로 분리한다. |
| init | 화면 로딩은 `GET .../init`으로 한다. |
| 조회/처리 | 화면 내부 데이터 조회와 처리는 같은 화면ID 아래 `search`, `find`, `create`, `update`, `delete`, `process`를 붙인다. |
| 예시 | 물품 화면ID `sell-receipt-prespecS2BList` -> `/catalog/goods/sell/receipt/prespecS2BList/search` |

| Action | Method | URI 패턴 | 예시 |
|---|---|---|---|
| 화면 로딩 | GET | `/{domain}/{subdomain}/{system}/{package}/{screenID}/init` | `/catalog/goods/sell/receipt/prespecS2BList/init` |
| 목록 조회 | POST | `/{domain}/{subdomain}/{system}/{package}/{screenID}/search` | `/catalog/goods/sell/receipt/prespecS2BList/search` |
| 단건 조회 | GET | `/{domain}/{subdomain}/{system}/{package}/{screenID}/find` | `/catalog/goods/sell/receipt/prespecS2BList/find` |
| 등록 | POST | `/{domain}/{subdomain}/{system}/{package}/{screenID}/create` | `/catalog/goods/sell/receipt/prespecS2BList/create` |
| 수정 | POST | `/{domain}/{subdomain}/{system}/{package}/{screenID}/update` | `/catalog/goods/sell/receipt/prespecS2BList/update` |
| 삭제 | POST | `/{domain}/{subdomain}/{system}/{package}/{screenID}/delete` | `/catalog/goods/sell/receipt/prespecS2BList/delete` |
| 일괄 처리 | POST | `/{domain}/{subdomain}/{system}/{package}/{screenID}/process` | `/catalog/goods/sell/receipt/prespecS2BList/process` |

기존의 BFF prefix 기반 경로, `/{system}/{package}/{screenID}/{action}` 또는 포탈/업무구분 기반 BFF 경로 형식은 표준으로 쓰지 않는다.

## 12. API URL 규칙

API URL은 도메인 API 또는 API 전용 Controller에 사용한다. 화면ID가 아니라 도메인과 Model 기준이다.

| 구분 | 규칙 |
|---|---|
| 패턴 | `/api/{domain}/{area}/{model}/{action}` |
| prefix | 반드시 `/api`로 시작한다. |
| domain | 우리 파트 기준 `catalog`를 고정 사용한다. |
| area | `14_PROCESS_MASTER`의 `업무영역` 선택값을 URL 세그먼트로 변환한다. `물품 -> goods`, `전시 -> display`, `검색 -> search` |
| system | API URL에는 포탈/시스템 구분 세그먼트를 넣지 않는다. |
| package | API URL에는 업무 패키지 또는 화면 패키지 세그먼트를 넣지 않는다. |
| model | 단수형 lower camelCase Model명을 사용한다. |

`14_PROCESS_MASTER`의 `Endpoint`는 `BFF ID(선택)` 여부와 관계없이 `/api/catalog/{area}/{model}/{action}`으로 계산한다.  
BFF 없이 단독으로 존재하는 프로세스도 동일한 API URL 규칙으로 `Endpoint`를 산출한다.

| Action | Method | URI 패턴 | 예시 |
|---|---|---|---|
| 목록 조회 | POST | `/api/{domain}/{area}/{model}/search` | `/api/catalog/goods/user/search` |
| 단건 조회 | GET | `/api/{domain}/{area}/{model}/find` | `/api/catalog/goods/user/find?userNumber=xxx` |
| 등록 | POST | `/api/{domain}/{area}/{model}/create` | `/api/catalog/goods/user/create` |
| 수정 | POST | `/api/{domain}/{area}/{model}/update` | `/api/catalog/goods/user/update` |
| 삭제 | POST | `/api/{domain}/{area}/{model}/delete` | `/api/catalog/goods/user/delete` |
| 일괄 처리 | POST | `/api/{domain}/{area}/{model}/process` | `/api/catalog/goods/user/process` |

## 13. URL 관련 금지 패턴

| 금지 | 대안 |
|---|---|
| `/api/admin/catalog/brand/123` | `/api/catalog/goods/brand/find?brandNumber=123` |
| `PUT /api/admin/catalog/brand/123` | `POST /api/catalog/goods/brand/update` |
| `DELETE /api/admin/catalog/brand/123` | `POST /api/catalog/goods/brand/delete` |
| `/api/admin/users/search` | `/api/catalog/goods/user/search` |
| `/api/admin/user/search/` | `/api/catalog/goods/user/search` |
| `/api/admin/user_search` | `/api/catalog/goods/user/search` |
| Controller 클래스 레벨 `@RequestMapping`으로 공통 경로 지정 | 메서드 단위 `@GetMapping`, `@PostMapping`에 전체 URI 지정 |

## 14. HTTP Method 규칙

표준 Method는 RESTful 자원 조작 방식이 아니라 프로젝트 명명규칙의 Action 방식에 맞춘다.

| Action | Method | 기준 |
|---|---|---|
| `init` | GET | 화면 로딩 |
| `search` | POST | 목록 조회 |
| `find` | GET | 단건 조회 |
| `create` | POST | 등록 |
| `update` | POST | 수정 |
| `delete` | POST | 삭제 |
| `process` | POST | 일괄 처리, 실행성 요청 |

신규 개발 기준으로 `PUT`, `PATCH`, `DELETE` Method를 기본 표준으로 사용하지 않는다. 기존 시스템 조사나 외부 API 기록에는 남길 수 있으나, 내부 표준 URL은 위 표를 따른다.

## 15. 요청/응답 명세 분리 규칙

마스터 시트는 식별자와 관계를 관리한다.

요청/응답/컬럼 수준의 상세 명세는 마스터 시트에 넣지 않는다. 상세 명세가 필요하면 추후 별도 시트를 만들 것이다.

예시:

| 시트명 | 역할 |
|---|---|
| `08_PROCESS_IO_SPEC` | 프로세스별 요청/응답 DTO |
| `09_FIELD_MAPPING` | 화면 필드와 API 필드 매핑 |
| `10_CODE_MAPPING` | 코드값 변환 규칙 |

현재 최소구성 관리대장에는 위 상세 명세 시트를 만들지 않는다.

## 16. 사람이 직접 수정해도 되는 영역

기존 자동 산출 행에서 직접 수정 가능한 컬럼은 아래로 제한한다.

- `사용여부`
- `업무영역`
- `BFF ID(선택)`
- `순서`
- `비고`

신규 매핑 행을 수동 추가할 때만 아래 ID 컬럼을 입력할 수 있다.

| 시트 | 입력 가능 컬럼 |
|---|---|
| `16_BFF_PROCESS_MAPPING` | `BFF ID`, `프로세스ID` |
| `17_PROCESS_PROGRAM_MAPPING` | `프로세스ID`, `프로그램ID` |

직접 수정하지 않는 영역:

- 그 외 나머지

예외를 넣어야 하면 값을 억지로 덮어쓰기보다 `비고`에 사유를 남긴다.

## 17. 운영/수식 보호 규칙

- 행을 실제 삭제하지 않는다. 제외가 필요하면 `사용여부=N`으로 관리한다.
- 삭제/제외 전용 시트는 만들지 않는다.
- 시트명은 임의로 변경하지 않는다. 수식 참조가 깨질 수 있다.
- 탭 순서를 바꿀 수는 있지만, 시트명을 바꾸는 작업은 금지한다.
- 수식 참조 범위나 시트 번호 체계를 바꿀 때는 관련 `INDEX`, `VLOOKUP`, 드롭다운, 매핑 수식을 같이 변경한다.
- 원천 파일을 먼저 저장한 뒤 관리대장을 열고, 외부 링크 갱신과 재계산을 수행한 뒤 관리대장을 저장한다.
- ZIP 내부 `externalLinks`가 새로 생성되지 않도록 원천 파일과 관리대장은 같은 S2B2 폴더 안에서 관리한다.
- 외부 연결 경고가 반복되면 파일명, 경로, 한글 NFC 정규화, 원천 보조열을 우선 확인한다.

## 18. 최종 판단 기준

이 관리대장의 목적은 화면 목록을 API 목록으로 억지 변환하는 것이 아니다.

목적은 아래 세 가지다.

1. BFF, 프로세스, 프로그램을 각각 독립 관리한다.
2. 실제 사용 관계는 매핑으로 표현한다.
3. URL과 Endpoint는 사람이 입력한 값이 아니라 규칙으로 계산한다.

따라서 새 화면이나 새 API가 생기면 아래 순서로 추가한다.

1. 프로그램이 새로 필요한지 판단한다.
2. 프로세스가 새로 필요한지 판단한다.
3. BFF가 새로 필요한지 판단한다.
4. 사용자가 원천 값을 추가하면 ID는 자동 계산한다.
5. 필요한 매핑 시트에 관계를 추가한다.
6. Endpoint는 수식 결과를 확인한다.

## 19. 추후 spec 개발 시 참고될 규칙

- BFF, Process, Program 관리 대장에서는 고려하지 않지만, 추후 spec 개발시 사용되는 규칙을 명시한다
- 관리 대장을 참고해서 다음 규칙들이 동작 할 예정이다.


### 1. 도메인/패키지/레이어 명명 규칙

도메인은 최상위 업무 영역이고, 하위패키지는 레이어 아래 기능 단위로 둔다.

| 구분 | 규칙 | 패턴 | 예시 | 주의 |
|---|---|---|---|---|
| 도메인 | 최상위 업무 영역 | `kr.s2b.{domain}` | `kr.s2b.admin`, `kr.s2b.catalog` | 모듈별 기준 패키지를 우선한다. |
| 하위패키지 | 기능 그룹 | `kr.s2b.{domain}.{layer}.{subpackage}` | `kr.s2b.admin.interfaces.systemadmin` | 도메인명과 하위패키지명을 섞지 않는다. |
| 업무 레이어 | 4-Layer 기준 분리 | `interfaces`, `application`, `domain`, `infrastructure` | Controller는 `interfaces`, Service는 `application` | 의존 방향은 `interfaces -> application -> domain`, `infrastructure -> domain` 기준이다. |
| 공통 패키지 | 공통 기능/설정/예외 | `kr.s2b.{domain}.core` | `kr.s2b.admin.core.file` | `core`는 일반 업무 레이어가 아니다. |
| Infrastructure 확장 | DB 외 외부 연계/캐시/Redis 구현 | `infrastructure/{type}` | `infrastructure/jdbc`, `infrastructure/external`, `infrastructure/cache` | Mapper는 `infrastructure.jdbc`에 둔다. |

### 2. 클래스/메서드 명명 규칙

| 구분 | 규칙 | 예시 |
|---|---|---|
| 패키지명 | 소문자만 사용 | `kr.s2b.admin.application.commoncode` |
| Java 클래스/인터페이스 | PascalCase | `UserCommandService`, `CreateUserReqDto` |
| 메서드/변수 | camelCase | `searchUsers()`, `userCommandService` |
| 상수 | UPPER_SNAKE_CASE | `DEFAULT_PAGE_SIZE` |
| 식별자 문자 | 영문/숫자만 사용 | `useYn`, `contractCategoryNumber` |
| 허용 약어 | 의미가 명확한 약어만 사용 | `Req`, `Rsp`, `Dto` |
| 지양 약어 | 의미가 줄어드는 약어 지양 | `createdDateTime`, `userName`, `userNumber` |

### 3. 클래스명과 패키지 위치 규칙

클래스명만 맞추지 말고 패키지 위치까지 같이 맞춘다.

| 계층 | 객체 | 클래스명 패턴 | 위치 패턴 |
|---|---|---|---|
| Interfaces | Controller | `{Model}Controller`, `{Model}RestController` | `interfaces/{subpackage}/controller` |
| Interfaces | Request DTO | `{Action}{Model}ReqDto` | `interfaces/{subpackage}/controller/dto` |
| Interfaces | Response DTO | `{Action}{Model}RspDto` | `interfaces/{subpackage}/controller/dto` |
| Interfaces | DTO Transfer | `{Model}{Command or Query}DtoTransfer` | `interfaces/{subpackage}/controller/transfer` |
| Application | Command | `{Action}{Model}Command` | `application/{subpackage}/commandservice/command` |
| Application | CommandService | `{Model}CommandService` | `application/{subpackage}/commandservice` |
| Application | Query | `{Action}{Model}Query` | `application/{subpackage}/queryservice/query` |
| Application | QueryService | `{Model}QueryService` | `application/{subpackage}/queryservice` |
| Domain | Domain Model | `{Model}` | `domain/model` |
| Domain | Repository Interface | `{Model}CommandRepository`, `{Model}QueryRepository` | `domain/repository/command`, `domain/repository/query` |
| Domain | QueryParam/QueryResult | `{Action}{Model}QueryParam`, `{Action}{Model}QueryResult` | `domain/query/param`, `domain/query/result` |
| Domain | CommandParam | `{Action}{Model}CommandParam` | `domain/command/param` |
| Infrastructure | MyBatis Mapper | `{Model}CommandRepositoryMapper`, `{Model}QueryRepositoryMapper` | `infrastructure/jdbc/command`, `infrastructure/jdbc/query` |
| Infrastructure | Cache Repository | `{Model}CommandCachingRepository`, `{Model}QueryCachingRepository` | `infrastructure/cache/command`, `infrastructure/cache/query` |
| Infrastructure | External DTO | `{Action}{Model}ExternalReqDto`, `{Action}{Model}ExternalRspDto` | `infrastructure/external/dto` |
| Infrastructure | Feign Client | `{Domain or Model}Client` | `infrastructure/external/client` |

### 4. 아키텍처 강제 규칙과 예외

아래 규칙은 이름뿐 아니라 패키지 위치와 레이어 의존성까지 같이 본다.

| 항목 | 규칙 | 이유 |
|---|---|---|
| Controller 위치 | `@Controller`, `@RestController`는 `interfaces..controller` 아래에 둔다. | Controller가 domain/infrastructure를 직접 호출하지 못하게 한다. |
| Service 위치 | `@Service`는 `application` 아래에 둔다. | 트랜잭션과 유스케이스 처리는 Application 계층 책임이다. |
| Mapper 위치 | `@Mapper`와 `RepositoryMapper`는 `infrastructure.jdbc` 아래에 둔다. | MyBatis 구현체는 Infrastructure 계층 책임이다. |
| DTO 위치 | `ReqDto`, `RspDto`는 `interfaces..controller.dto` 아래에 둔다. | HTTP 요청/응답 객체는 Interfaces 계층에만 둔다. |
| QueryParam/QueryResult 위치 | `QueryParam`은 `domain.query.param`, `QueryResult`는 `domain.query.result`에 둔다. | Repository interface와 조회 결과 계약은 Domain 계층에 둔다. |
| Repository interface 위치 | `Repository` interface는 `domain.repository` 아래에 둔다. | Domain이 저장소 계약을 소유하고 Infrastructure가 구현한다. |
| RepositoryMapper 구현 | `RepositoryMapper`는 Repository interface를 구현해야 한다. | MyBatis mapper가 Domain 저장소 계약의 구현체가 되도록 한다. |
| Transfer 구현 | `Transfer`는 MapStruct `@Mapper`가 붙은 interface 또는 abstract class여야 한다. | 레이어 간 객체 변환을 흩트리지 않는다. |
| CommandService 트랜잭션 | `CommandService`는 클래스 또는 public 메서드에 `@Transactional`이 필요하다. | CUD 트랜잭션은 Application 계층에서 관리한다. |
| Domain 모델 setter | `domain.model`의 public setter는 금지한다. | Domain Model은 Builder/정적 생성/행위 메서드 중심으로 다룬다. |
| CommandService 파라미터 | public 메서드 파라미터는 `Command` 타입이어야 한다. | DTO나 primitive를 직접 받으면 레이어 계약이 흐려진다. |
| QueryService 시그니처 | public 메서드는 `Query`를 받고 `QueryResponse`를 반환한다. | 조회 계약을 QueryService에서 일관되게 강제한다. |
| QueryRepository 시그니처 | `QueryParam`을 받고 `QueryResult`, `List`, `Optional`을 반환한다. | Repository 계약을 Domain 레이어에서 명확히 한다. |
| CommandRepository 파라미터 | `domain.*` 타입을 받는다. | Command 객체를 Repository에 직접 넘기지 않는다. |
| 필드 주입 금지 | `@Autowired` 필드 주입을 사용하지 않는다. | 생성자 주입을 사용한다. |
| Controller 트랜잭션 금지 | `interfaces` 레이어에 `@Transactional`을 붙이지 않는다. | 트랜잭션은 Application 레이어에서 관리한다. |
| `@RequestBody` 검증 | `@RequestBody` 파라미터에는 `@Valid`를 붙인다. | Bean Validation을 동작시킨다. |
| JPA 어노테이션 금지 | `domain.model`에 `@Entity`, `@Table`, `@Column`을 사용하지 않는다. | 프로젝트 기준은 MyBatis다. |
| 순환 의존성 금지 | `kr.s2b.{domain}.(*)..` 슬라이스 간 순환 의존성이 없어야 한다. | 하위패키지 간 순환 참조를 막는다. |
| `core` 예외 | `core` 아래 공통 모듈은 일반 업무 규칙과 일부 다를 수 있다. | 공통/예외 패키지로 분리한다. |
| Transfer suffix | `Transfer`, `DtoTransfer` suffix를 정확히 지킨다. | suffix 기반 검사에서 빠지지 않게 한다. |
