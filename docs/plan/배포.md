# 배포 — 실제 서버에서 하나의 URL 로 쓰기

2026-09-05. 개발용 2포트(웹 5173 + API 8787) 실행을 **운영용 1포트**로 바꾸고, 실제 서버에 올리는 데 필요한 것을 정리한다.
지금 이 저장소에서 확인한 것과 확인하지 못한 것을 구분해 적는다.

## 0. 지금 무엇이 되는가

| 실행 | 명령 | 접속 | 용도 |
|---|---|---|---|
| 개발 | `pnpm dev` | 웹 5173 + API 8787 (Vite 가 `/api`·`/exports` 프록시) | 코드 수정하며 개발 |
| **운영(한 포트)** | `pnpm serve` (= `pnpm build:web && pnpm start`) | **8787 하나** | 실제 사용·시연 |
| 컨테이너 | `docker compose up -d` | 8787 하나 | 서버 배포 |
| 정적 데모 | GitHub Pages | https://parkh37t.github.io/con-ai/ | 스냅샷 열람 전용 |

> **데모 빌드와 섞지 않는다**: `pnpm demo:build`(Pages 용)와 `pnpm build:web`(운영용)은 **같은 `apps/web/dist` 에 쓴다**.
> 데모 빌드는 base 가 `/con-ai/` 라 자산을 `/con-ai/assets/…` 로 요청하고 서버 대신 스냅샷을 읽는다 — 운영 서버에서는 동작하지 않는다.
> 운영으로 띄우기 전에는 반드시 `pnpm build:web`(또는 `pnpm serve`)으로 다시 빌드한다. 서버는 이런 경로에 HTML 을 주지 않고 404 로 알린다.

`pnpm start` 는 `tsx apps/api/src/server.ts` 다. 워크스페이스 패키지(`packages/*`)가 `exports: "./src/index.ts"` 로
**TypeScript 소스를 그대로 내보내기 때문에** 컴파일 산출물(`apps/api/dist/server.js`)이 없다. 빌드 단계를 새로 만드는 대신
런타임에 tsx 로 실행한다(원래 개발 실행과 같은 방식). 웹만 Vite 로 빌드해 API 가 그 결과를 함께 제공한다.

## 1. 왜 GitHub Pages 로는 안 되는가

Pages 는 **정적 파일 호스팅**이다. HTML·CSS·JS 만 돌려줄 뿐 서버 프로세스를 실행하지 않는다. 이 제품은 네 가지가 서버에서 돌아야 한다.

- **Node 프로세스** — 생성 파이프라인(문맥 구성 → 모델 호출 → 스키마·참조 검증 → 렌더 → 저장), 순차 작업 큐, 승인 게이트.
- **Chromium** — V3 실행 검사와 AS-IS 분석(URL 방문·스크린샷·구조 추출)은 Playwright 로 실제 브라우저를 띄운다.
- **영속 저장소** — 프로젝트·화면·revision·산출물 HTML·검증 결과·코멘트·승인이 SQLite(`con-ai.db`)에, 완료본이 `exports/` 에 쌓인다.
- **모델 호출** — `ANTHROPIC_API_KEY`/토큰은 서버에만 둔다. 브라우저에 내려보내면 그 순간 유출된다(설계 §5, ADR 0014).

현재 Pages 에 올라간 것은 `pnpm demo:snapshot` 이 만든 **실행 결과 스냅샷 데모**다. 화면 검토·코멘트·완료 흐름을 눌러볼 수 있지만
새 URL 분석과 실제 모델 호출은 동작하지 않는다(실패로 표시되며 성공으로 위장하지 않는다). 홍보·리뷰용이지 업무용이 아니다.

## 2. 실제로 필요한 것 3가지

1. **Node 22 + Chromium 을 실행할 수 있는 컨테이너 호스트** — 파이프라인과 실행 검사(V3)·AS-IS 분석이 브라우저를 띄우므로, 함수형(서버리스) 런타임이나 정적 호스팅으로는 안 된다.
2. **영속 볼륨** — SQLite DB 와 내보내기 산출물이 재시작·재배포 후에도 남아야 한다. 디스크가 사라지는 호스트는 승인 이력과 v1.0 산출물을 잃는다.
3. **인증(접근 통제)** — 지금 제품에는 로그인이 없다. 주소를 아는 누구나 고객 기획 문서를 열람·수정하고 모델 비용을 발생시킬 수 있다.

## 3. 호스트 선택지

| 호스트 | 장점 | 단점 | 이 제품에 맞나 |
|---|---|---|---|
| **사내 서버·VM (Docker)** | 사설망 안에 둘 수 있고 디스크·백업을 직접 통제. Chromium 용량 제약 없음 | 서버·OS·HTTPS 를 직접 관리 | **가장 맞다** — 고객 기획 문서를 다루고 인증이 아직 없다 |
| Fly.io | 볼륨 지원, 지역 선택, 배포 간단 | 볼륨이 인스턴스에 묶여 스케일아웃 어려움, 이미지 용량 과금 | 가능. 외부 노출이라 앞단 인증이 필수 |
| Render | Docker 배포·디스크 지원, 관리 편함 | 무료 등급은 슬립·디스크 없음. 이미지가 커서 빌드 느림 | 가능. 유료 디스크 필수 |
| Railway | 배포가 가장 빠름, 볼륨 지원 | 사용량 과금 변동, 사설망 배치 어려움 | 시험용으로 가능 |
| Google Cloud Run | 확장·운영 부담 적음, 컨테이너 그대로 | 파일시스템이 휘발성 — **SQLite 를 쓸 수 없다**. Cloud SQL(PostgreSQL) + GCS 전환 또는 최근의 볼륨 마운트 구성이 별도로 필요 | 지금 구조로는 부적합(§6 PostgreSQL 전환 후 재검토) |
| Azure Container Apps | 사내 네트워크(VNet) 통합, 확장 | 영속 저장은 Azure Files 마운트 구성 필요, 설정이 복잡 | 사내망 요건이 강하면 검토 |

**추천: 사내 서버 또는 사내망 VM 에 Docker 로 배포하고 VPN·사설망 안에서만 접근한다.** 이유는 하나다 — 이 제품은
고객 기획 문서와 요구사항을 다루는데 **아직 인증이 없다**. 인증(ADR 0014 1단계)이 들어오기 전까지 공개 인터넷에 두지 않는다.

## 4. 배포 절차 (사내 서버 기준)

```bash
# 1) 저장소 받기
git clone https://github.com/parkh37t/con-ai.git && cd con-ai

# 2) 실행 설정 (.env — 이미지에 들어가지 않고 실행 시에만 주입된다)
cp .env.example .env
#   MODEL_ADAPTER=fixture      더미(모델 호출 없음). 먼저 이걸로 띄워 동작을 확인한다
#   MODEL_ADAPTER=anthropic    실제 호출. ANTHROPIC_API_KEY 또는 ANTHROPIC_AUTH_TOKEN 을 채운다
chmod 600 .env

# 3) 영속 볼륨 (컨테이너는 비루트 uid 1000 으로 실행된다)
sudo mkdir -p /srv/con-ai/data && sudo chown -R 1000:1000 /srv/con-ai/data

# 4) 실행 (최초 1회 이미지 빌드 — 수 분, Chromium 포함)
CON_AI_DATA_DIR=/srv/con-ai/data docker compose up -d --build
docker compose logs -f          # 접속 주소·인증 경고 확인
curl -s localhost:8787/healthz  # {"status":"ok",...}
```

`docker-compose.yml` 의 볼륨 기본값은 `./var/data` 다(gitignore 되며 검토 자료가 있는 `data/` 와 겹치지 않는다).
실제 서버에서는 위처럼 `CON_AI_DATA_DIR` 로 **저장소 밖 경로**를 주는 것을 권한다.

**5) 리버스 프록시(HTTPS)와 접근 제어** — 컨테이너는 평문 HTTP 8787 이다. 앞에 nginx·Caddy 를 두고 TLS 를 종료하며,
같은 자리에서 접근 제어(사내 SSO, mTLS, 최소한 Basic 인증)를 건다. 포트를 외부에 직접 열지 않는다
(`docker-compose.yml` 의 포트 매핑을 `127.0.0.1:8787:8787` 로 바꾸면 프록시만 붙일 수 있다).

```nginx
# 예시 — 사내망에서만 접근, HTTPS 종료, 프록시에서 인증
server {
  listen 443 ssl;
  server_name con-ai.내부도메인;
  allow 10.0.0.0/8; deny all;              # 사내망만
  auth_basic "con-ai"; auth_basic_user_file /etc/nginx/.htpasswd;
  client_max_body_size 20m;
  location / {
    proxy_pass http://127.0.0.1:8787;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 300s;               # 생성 작업은 수십 초~수 분 걸린다
  }
}
```

컨테이너 없이 서버에서 바로 띄우려면(Node 22·pnpm·Chromium 이 이미 있는 경우):
`pnpm install --frozen-lockfile && set -a; source .env; set +a; pnpm serve` — 같은 8787 한 포트로 뜬다.

## 5. 이미지에서 정한 것과 그 근거

- **베이스 `node:22-bookworm` + Chromium 직접 설치**. `mcr.microsoft.com/playwright:v1.63.0-noble` 을 먼저 검토했지만,
  레지스트리에서 그 이미지의 config 를 확인한 결과 **Node 24** 로 만들어진다(빌드 이력에 `ARG NODE_VERSION=24`).
  이 저장소는 Node 22 로 고정돼 있고(`package.json engines`, `.node-version`, CLAUDE.md), 저장소가 쓰는 `node:sqlite` 는
  Node 22 에서 실험 기능이라 런타임 메이저를 임의로 올리면 동작이 달라질 수 있다. 또 그 이미지는 firefox·webkit 까지 포함해
  쓰지 않는 용량이 크다. 그래서 Node 22 이미지에 `playwright@1.63.0 install --with-deps chromium` 으로 Chromium 만 넣는다.
  Playwright 버전은 `apps/api/package.json` 과 **같아야 한다**(Dockerfile 의 `ARG PLAYWRIGHT_VERSION`).
- **단계**: 의존성 설치(`pnpm install --frozen-lockfile`, 매니페스트만 먼저 복사해 캐시) → 웹 빌드(`pnpm build:web`) →
  런타임 이미지로 `/app` 복사. 워크스페이스 패키지가 `node_modules` 안에서 상대 심볼릭 링크로 연결되므로 통째로 옮긴다.
- **실행**: `node --import tsx --enable-source-maps apps/api/src/server.ts` — 셸·pnpm 을 거치지 않아 `docker stop` 의
  SIGTERM 이 서버 프로세스에 바로 간다.
- **비루트**: `node` 사용자(uid 1000). `/data` 는 이미지에서 미리 만들고 소유권을 맞춘다. 호스트 바인드 마운트를 쓰면
  호스트 폴더 소유자도 uid 1000 이어야 쓸 수 있다.
- **`.dockerignore`**: `node_modules`(호스트 심볼릭 링크는 컨테이너에서 깨진다), `dist`, `.env`(비밀값), `.git`, `.local`,
  `exports`, `test-results`, `playwright-report`, `data/review`(고객 자료), `e2e` 를 뺀다.
  `apps/web/public/demo`(약 560KB, Pages 스냅샷 데모 전용)도 **뺀다** — 일반 빌드는 이 파일들을 참조하지 않는다
  (`apps/web/src/demo-mode.ts`: `VITE_DEMO=1` 일 때만 사용). 제외한 상태로 웹 빌드가 정상 동작하는지 확인했다.

## 7. 보안 점검표 (공개 전 확인)

- [ ] **인증** — 프록시 인증 또는 ADR 0014 1단계 없이는 사설망 밖에 두지 않는다. 서버는 시작할 때마다 이 경고를 출력한다.
- [ ] **HTTPS** — 리버스 프록시에서 TLS 종료. 평문 8787 을 외부에 직접 노출하지 않는다.
- [ ] **모델 키는 서버에만** — `.env`(권한 600, 커밋 금지, 이미지 제외). 로그·API 응답에 값이 나가지 않는다
      (`/api/meta`·`/healthz` 는 종류만 표시). 브라우저에는 어떤 자격 증명도 내려보내지 않는다.
- [ ] **생성 HTML 격리** — `/api/artifacts/:id/html` 은 CSP `default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; img-src data:`
      로 내려가고 iframe `sandbox="allow-scripts"` 안에서만 표시된다. 외부 자원을 불러오지 못한다.
- [x] **분석 대상 URL 제한 (SSRF)** — **구현됨 — 기본 차단, 사내 분석은 `ASIS_ALLOW_PRIVATE=1` 또는 `ASIS_ALLOWED_HOSTS` 로 허용**
      (`apps/api/src/ssrf.ts`). http/https 만 받고 사설(10/8·172.16/12·192.168/16)·루프백(127/8·`::1`)·링크로컬
      (169.254/16 — 클라우드 메타데이터 169.254.169.254 포함·fe80::/10)·0/8·100.64/10(CGNAT)·192.0.0/24·문서용
      (192.0.2/24·198.51.100/24·203.0.113/24)·224/4·240/4·IPv6 ULA(fc00::/7)·IPv4-mapped IPv6(`::ffff:10.0.0.1`)를 막는다.
      호스트 이름은 A/AAAA 를 모두 해석해 **하나라도** 차단 대역이면 거부하고, 해석 실패도 거부한다(fail closed).
      막는 지점은 세 곳이다 — ① 접수(`POST …/asis-analyses` → 400 `blocked_url`, 문서를 만들지 않는다),
      ② 러너의 나가는 요청마다 `page.route` 로 abort + 리다이렉트 각 단계 검사, ③ `goto` 후 최종 URL 재검사
      (위반이면 캡처·구조 추출 없이 `failed(blocked)`). 차단된 하위 리소스는 분석을 실패시키지 않고
      분석 문서의 `blocked_requests` 에 건수만 남는다. 예외는 이 서버 자신의 데모 페이지 `/asis-sample`
      (같은 호스트·**같은 포트**·정확히 그 경로) 하나뿐이다 — 임의의 localhost 경로는 열리지 않는다.
      **사내 배포 권장 설정**: 사내 스테이징을 분석해야 하면 `ASIS_ALLOW_PRIVATE=1` 로 전부 열지 말고
      `ASIS_ALLOWED_HOSTS=legacy.staging.corp.example,.internal.corp.example` 처럼 대상만 열고,
      `ASIS_BLOCKED_HOSTS` 에 메타데이터 호스트명(`metadata.google.internal` 등)을 넣는다(`.env.example` 참고).
      **남은 한계**: 우리가 해석한 IP 와 chromium 이 실제로 접속할 때 해석하는 IP 는 다른 조회라 DNS 재바인딩을
      완전히 막지는 못한다. 또 리다이렉트 중간 단계는 Playwright 가 route 핸들러를 다시 부르지 않아 **탐지는 하지만
      요청 자체를 막지는 못한다**(캡처는 막는다). 사내망에서는 컨테이너 egress 를 프록시로 제한하는 것이 확실하다.
- [ ] **업로드·입력 크기 제한** — 프록시에서 본문 크기를 제한한다(`client_max_body_size`).
- [ ] **로그에 비밀값 금지** — 키·토큰 값은 출력하지 않는다(어댑터 종류·인증 방식만). 새 로그를 추가할 때도 지킨다.
- [ ] **볼륨 권한** — `/data` 는 컨테이너 사용자만 쓰기 가능. 백업본도 같은 수준으로 보호한다.
- [ ] **고객 데이터 위치** — `data/review/` 는 커밋하지 않는다. 볼륨 경로를 저장소 밖으로 두면 섞이지 않는다.
