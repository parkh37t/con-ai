# 세로 조각 v0 계약 (패키지 간 인터페이스)

2026-09-05. 병렬 구현을 위해 패키지 경계·타입·API 를 먼저 고정한다. 타입은 `@con-ai/schemas` 를 우선 쓰고, 여기 정의한 것은 각 패키지 `src/types.ts` 에 그대로 둔다. 바꿔야 하면 이 문서와 types.ts 를 같이 고친다.

## 1. 저장 레코드 (apps/api, node:sqlite)

테이블 `documents(kind TEXT, id TEXT, revision INTEGER, json TEXT, created_at TEXT, updated_at TEXT, PRIMARY KEY(kind,id))` 하나에 종류별 JSON 문서를 저장한다. `artifact_html(artifact_id TEXT PRIMARY KEY, html TEXT)` 는 HTML 본문. DB 파일은 `.local/con-ai.db`(gitignore). 저장 시 revision 을 비교해 오래된 저장을 거부한다(설계 §11).

| kind | 필드 (schemas 타입을 쓰면 그 이름) |
|---|---|
| `project` | `id, name, org, description, profile_id('s2b-learned-v1'), created_at` |
| `requirement` | `id, project_id, external_id('REQ-…'), title, body, criteria:[{id('AC-…'), text, kind:'ui'\|'non_ui'}]` |
| `ia_node` | schemas `IANode` — P1-05 로 optional 확장: `external_id('IA-2.3.1')`, `issued{by,at,reason}`, `aliases[]`, `requirement_ids[]`, `asis_ref`, `change_reason`, `functions[]`(FN 은 이 문서 안에 산다) |
| `screen` | `id, project_id, external_id, title, shell, device, status:'draft'\|'review'\|'approved', current_revision_id?, version?('1.0'), aliases:[]` |
| `screen_revision` | `id, screen_id, revision_no(1..), spec: ScreenSpec, spec_hash, artifact_id, job_id, based_on_revision_id?, change_summary?: ChangeSummary, created_at` |
| `job` | schemas `GenerationJob` 필드 + `request: SliceGenerationRequest, adapter:'anthropic'\|'fixture', model, prompt_text, context_summary, result?:{revision_id, artifact_id}` |
| `artifact` | schemas `Artifact` (kind 'html', content_hash=sha256(html), status) |
| `validation_result` | schemas `ValidationResult` (artifact_hash 로 조회) |
| `comment` | `id, screen_id, revision_id, artifact_hash, target:'screen'\|'description', element_id?, section_id?, case_id?, display_no?, author, role:'planner'\|'designer'\|'publisher'\|'developer'\|'client', text, blocking:boolean, status:'open'\|'resolved'\|'wont_fix', resolved_by_revision_id?, created_at` |
| `approval` | schemas `Approval` + `version:'1.0', export_path, files:[{path, sha256}]` |
| `reference` | 포트폴리오 골든 예시: `id, project_id?, title, category:'list'\|'detail'\|'popup'\|'form', description, spec: ScreenSpec, tags:[], source:'S2B 학습 규격 적용 합성 예시'` |
| `prompt_template` | schemas `PromptTemplate` (version, 본문) |

## 2. 생성 요청 (웹 → API → 워커)

```ts
// packages/prompt-templates/src/types.ts
export interface SliceGenerationRequest {
  screen_id: string                       // 내부 UUID
  task_type: 'create' | 'edit' | 'clone_reference'
  purpose: string                         // 변경 목적
  scope?: string                          // 변경 범위
  requirement_ids: string[]               // 내부 UUID (요구사항)
  criterion_ids: string[]                 // 'AC-…' 외부 ID
  reference_ids: string[]                 // reference 레코드 id (참조 복제·참고)
  cases: Array<'normal' | 'empty' | 'error' | 'permission' | 'processing'>
  keep_conditions: string[]               // 유지 조건 (잠긴 요소·데이터 계약)
  roles: string[]
  device: 'desktop' | 'mobile'
  base_revision_id?: string               // edit 일 때 기준 revision
  comment_ids?: string[]                  // edit 일 때 반영할 코멘트
  prompt_override?: string                // 기획자가 직접 쓴 프롬프트 (있으면 자동 조립 대신 사용, 문맥은 그대로 첨부)
}
export interface GenerationContext {      // 문맥 구성 결과 (설계 §8: 대상에 연결된 자료만)
  project: { name: string; org: string; profile_id: string }
  screen: { external_id: string; title: string; shell: string; device: string }
  requirements: Array<{ external_id: string; title: string; body: string; criteria: Array<{ id: string; text: string; kind: 'ui' | 'non_ui' }> }>
  references: Array<{ id: string; title: string; category: string; spec: unknown }>
  base_spec?: unknown                     // edit 기준 ScreenSpec
  comments?: Array<{ id: string; role: string; author: string; text: string; element_id?: string; case_id?: string; target: string }>
  profile_rules: string[]                 // S2B 학습 규격 요약 문장
  baseline_id: string
}
export interface AssembledPrompt { system: string; user: string; template_version: string; context_summary: string[] }
export function assemblePrompt(req: SliceGenerationRequest, ctx: GenerationContext): AssembledPrompt
export function assembleRevisionPrompt(ctx: GenerationContext, instruction: string): AssembledPrompt
```

## 3. 모델 어댑터 (packages/model-adapter)

```ts
export interface ModelAdapter {
  readonly kind: 'anthropic' | 'fixture'
  readonly model: string                  // anthropic: 모델 ID, fixture: 'fixture'
  generateSpec(input: { prompt: AssembledPrompt; ctx: GenerationContext; req: SliceGenerationRequest }): Promise<AdapterResult>
  reviseSpec(input: { prompt: AssembledPrompt; ctx: GenerationContext; req: SliceGenerationRequest; current: ScreenSpecShape }): Promise<AdapterResult>
  draftRevisionPrompt(input: { ctx: GenerationContext; current: ScreenSpecShape; comments: GenerationContext['comments'] }): Promise<{ prompt: string; rationale: string }>
}
export interface AdapterResult {
  output: GenerationOutputInput            // schemas GenerationOutput 입력 형태 (screen_spec, trace_proposals, unresolved, change_summary). 검증은 서버가 다시 한다
  raw_text?: string
  usage?: { input_tokens: number; output_tokens: number }
  stop_reason?: string
}
export function createAdapter(env: NodeJS.ProcessEnv): ModelAdapter   // MODEL_ADAPTER=anthropic|fixture (기본 fixture), MODEL_ID (기본 claude-opus-5)
```
- anthropic: `@anthropic-ai/sdk` `client.messages.parse` + `zodOutputFormat` 로 구조화 출력. 모델 기본 `claude-opus-5`, `max_tokens: 16000`, `output_config.effort: 'high'`, thinking 은 생략(기본 adaptive). 오류는 SDK 타입별로 잡고 `stop_reason === 'refusal'` 을 처리한다. 키는 환경변수(`ANTHROPIC_API_KEY`)에서만 읽고 절대 로그·응답에 넣지 않는다.
- fixture: 네트워크 없이 결정적으로 명세를 만든다(참고 spec 을 목적·CASE·요구사항에 맞게 변형; edit 는 코멘트 문장에서 라벨 변경·메시지 추가·필수 표시 등 단순 규칙 적용). 화면에는 "더미 어댑터" 로 표시된다.

## 4. 렌더러 (packages/renderer)

```ts
export interface RenderInput {
  spec: ScreenSpecShape
  profile: RenderProfile                  // 'S2B 학습 규격' 프로파일: shell 클래스, 설명 순서, 번호 규칙
  dummy: Record<string, unknown[]>        // fixture_id → 행 목록 (states[].fixture_id 와 일치)
  meta: { screen_title: string; requirements: Array<{ external_id: string; title: string; criterion_ids: string[] }>; revision_label: string; generated_by: string }
}
export interface RenderOutput { html: string; description: DescriptionModel; element_index: Array<{ element_id: string; section_id: string; display_no: string }> }
export function renderScreen(input: RenderInput): RenderOutput
export const S2B_LEARNED_PROFILE: RenderProfile
```
- HTML 은 오프라인 단일 파일(외부 CDN·폰트 없음). 구조: `.root-shell > .screen-wrap`(목업) + `#right-panel`(설명). 팝업 shell 은 `.popup-shell` + `.spec-side`.
- 설명 순서(설계 §9): 화면 ID 제목 → 화면명·목적·REQ → CASE → 처리 흐름 → 정책 → 데이터 매핑 → 영역·필드 설명 → 메시지 표. 설명의 번호와 화면의 번호는 같은 `element_index` 에서 만든다.
- 모든 영역·요소에 `data-element-id`, `data-section-id`, `data-display-no`; 설명 항목에도 같은 `data-element-id`.
- 동작: 검색=더미데이터 필터, 정렬=기본 정렬, 팝업=간단 모달, 다운로드=명세 컬럼으로 CSV 생성, CASE 전환=`data-case`. 실제 API 호출 없음.
- postMessage(부모가 있을 때만): iframe→부모 `{type:'con-ai:element-click', element_id, section_id, case_id, target:'screen'|'description', display_no}`; 부모→iframe `{type:'con-ai:set-case', case_id}`, `{type:'con-ai:highlight', element_id}`. 부모가 없으면 툴바의 CASE 버튼으로 전환.

## 5. 검증 (packages/validators)

```ts
export const REQUIRED_CHECKS: string[]   // 승인에 필수인 check_id 목록
export function runV1(spec: unknown, opts: { required_cases: string[] }): ValidationResult[]      // 스키마·참조·필수 CASE·수용조건 연결
export function runV2(html: string, spec: ScreenSpecShape, profile: RenderProfile): ValidationResult[]  // shell·설명 순서·요소 id·번호 일치
export function runV3(html: string, opts: { timeout_ms?: number }): Promise<ValidationResult[]>     // Playwright: 콘솔 오류 0, CASE 전환, 검색 필터. 브라우저를 못 띄우면 status 'error' 로 기록(통과 아님)
export function runAll(...): Promise<ValidationResult[]>
```
- check_id 예: `V1.schema`, `V1.references`, `V1.required_cases`, `V1.criteria_linked`, `V2.shell`, `V2.description_order`, `V2.element_ids`, `V2.display_numbers`, `V3.console_errors`, `V3.case_switch`, `V3.search_filter`. 각 결과는 schemas `ValidationResult`(artifact_hash, stage, status, required, evidence, checker_version).
- fixtures/screen-specs 의 bad-mapping 은 V1 fail, missing-case 는 V1.required_cases fail 이어야 한다.

## 6. 생성 파이프라인 (workers/generation)

```ts
export interface PipelineDeps { store: Store; adapter: ModelAdapter; render: typeof renderScreen; validate: (html, spec) => Promise<ValidationResult[]>; now: () => string }
export async function runGenerationJob(jobId: string, deps: PipelineDeps): Promise<void>
```
단계: `context_build → spec_generate → schema_check(ScreenSpec 파싱+참조) → render → validate → persist`. 각 단계 진입 시 job.stage 갱신, 실패 시 `status:'failed', failure:{code, message, stage}`. 성공 시 screen_revision·artifact(status `validation_pending` → 필수 검사 전부 pass 면 `review_ready`)·validation_result 저장, job.result 기록. 실패한 작업은 이전 HTML 을 결과로 연결하지 않는다.

**정적 데모(배포 주소)의 같은 경로.** 위 RTM·IA 노드 5개 경로는 서버 없이도 브라우저 안에서 같은 응답 모양으로
처리된다(`apps/web/src/demo-rtm.ts`). 커버리지 계산·발번 판정·스키마 검사는 **서버와 같은 모듈**(`@con-ai/domain`,
`@con-ai/schemas`)을 그대로 부르고, 저장만 이 브라우저의 localStorage 로 간다. 저장하지 못하면 응답에
`storage_warning` 을 실어 화면이 알린다. 다른 경로(생성·AS-IS 분석 등)의 데모 동작은 종전과 같다.

## 10. 샘플 데이터 (시드)

프로젝트 "와일리 컨버전스 샘플 — 파트너 견적 포털"(가상). 요구사항 5건(각 수용조건 2~3, 그중 1건은 비UI 조건 포함), To-Be IA(포털 > 견적 > 목록/상세/등록 팝업), 화면 3개(`SAMPLE-quote-list`, `SAMPLE-quote-detail`, `SAMPLE-quote-create-popup`), 레퍼런스 3개(목록/상세/팝업 골든, S2B 학습 규격 적용), 더미 데이터(정상 5행·검색 결과·빈값·오류), 프롬프트 템플릿 v1(설계 §8 7구역, 내부 계약 문장 포함). 실제 고객 데이터·S2B 원문은 쓰지 않는다.

| 생성 요청 | 문맥 구성 실패(없는 요구사항·레퍼런스·기준 revision)는 400 으로 즉시 알리고 작업을 만들지 않음 | 실패 작업 누적 방지 |

## 12. AS-IS 분석 (4단계 프로세스 ①, 2026-09-05 추가)

기획자가 대상 서비스 URL 을 입력하면 서버가 Playwright 로 방문해 스크린샷·구조를 수집하고, 모델 어댑터가 페인포인트 초안을 만들며, 기획자가 채택/거부로 확정한다.

**저장 (kind `asis_analysis`)**: `{id, project_id, url, note?, status:'queued'|'running'|'succeeded'|'failed', failure?:{code:'navigation'|'browser'|'draft'|'blocked'|'internal', message}, blocked_requests?, adapter, model, created_at, finished_at?, structure?, screenshots?:{desktop: asset_id, mobile: asset_id}, summary?, pain_points:[{id, area, severity:'high'|'medium'|'low', description, evidence, suggestion, status:'proposed'|'adopted'|'rejected'}]}`. 스크린샷 PNG 는 `asis_asset(asset_id TEXT PRIMARY KEY, png BLOB)` 테이블.

**structure**: `{title, description?, lang?, headings:[{level,text}](h1~h3, 상위 30), nav_links:[{text,href}](상위 30), forms:[{name?, fields:[{type,label?,name?}]}], buttons:[text](상위 30), counts:{links, images, images_without_alt, tables, fields_without_label, iframes}}`

**API**
| 메서드·경로 | 요청 | 응답 |
|---|---|---|
| POST `/api/projects/:id/asis-analyses` | `{url, note?}` (http/https 만) | 202 `{analysis_id}` |
| GET `/api/projects/:id/asis-analyses` | | 목록 요약(id, url, status, 페인포인트 수, created_at) |
| GET `/api/asis-analyses/:id` | | 전체 문서 |
| PATCH `/api/asis-analyses/:id/pain-points/:pid` | `{status, revision}` | 갱신된 문서 |
| GET `/api/asis-assets/:id` | | image/png |
| GET `/asis-sample` | | 합성 레거시 데모 페이지(의도된 페인포인트 포함; 분석 데모·e2e 대상) |

**러너(apps/api)**: chromium launch 는 validators 와 같은 executablePath 규칙. `goto(url, {waitUntil:'domcontentloaded', timeout: 20_000})` 후 데스크톱 1280×800 fullPage PNG + 모바일 390×844 PNG, `page.evaluate` 로 structure 추출. 실패는 code 와 함께 failed 로 기록(성공으로 위장 금지). 같은 순차 큐 사용.

**ModelAdapter 추가 메서드**: `draftPainPoints({url, note?, structure}): Promise<{summary, pain_points:[{area, severity, description, evidence, suggestion}]}>` — anthropic 은 구조화 출력, fixture 는 규칙 기반(레이블 없는 필드, alt 없는 이미지, h1 없음/중복, 내비 링크 과다, 모호한 버튼 문구, caption 없는 표, iframe 등). `id`(`PP-001`…)와 `status:'proposed'` 는 서버가 부여.

**웹**: `#/asis` 목록 + 실행 폼(URL·메모), `#/asis/:id` 상세(상태 폴링, 데스크톱/모바일 스크린샷 토글, 구조 요약, 페인포인트 표 + 채택/거부, 요약). 홈·상단 내비에 "AS-IS 분석" 링크.

**주의**: 이 개발 컨테이너는 외부 egress 가 프록시 정책에 막힐 수 있어 외부 URL 분석이 failed(navigation) 가 될 수 있다. 사용자 PC 에서는 제약 없다. e2e 는 자체 제공 `/asis-sample` 을 대상으로 한다.
