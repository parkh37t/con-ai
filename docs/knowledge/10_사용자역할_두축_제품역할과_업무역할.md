# 10. 사용자 역할의 두 축 — 제품 사용자 역할(승인 권한)과 업무 사용자 역할(화면 이용 역할·포털)

설계는 "사용자"를 두 축으로 쓴다 — 이 제품을 조작하는 **제품 사용자**(기획자·기획 리더·디자이너·개발자·QA, 승인 권한 축)와 생성할 화면을 이용하는 **업무 사용자 역할**(프로젝트 생성·프롬프트 '대상'의 독립 입력, 포털·PC/모바일과 나란한 축)이며, 후자의 값 목록은 원본 어디에도 없다. 출처 범위: 설계 §2·§3·§4·§5·§6·§8·§9·§10·§12·§13·§14·§15, 보고서 §3·§4·§6, 개발프롬프트 9·11·27행, `data/review/` CSV 실측(2026-09-05), 저장소 코드 초안(`packages/schemas`, `packages/domain`, `fixtures`).

> 이 관점의 지식 JSON 은 반박 검증을 거치지 못했다. 아래 사실은 모두 원문과 직접 대조했고 숫자는 CSV 로 재집계했다. 대조 결과 정정한 항목은 §4.9 와 §6 에 "정정" 으로 표시했다.

## 2. 핵심 개념·흐름

### 2.1 축 A — 제품 사용자와 승인 권한 제안 (설계 §2 표, 17~22행)

| 사용자 | 주 작업 | 승인 권한 제안 |
|---|---|---|
| 기획자 | 자료 등록, 추출 정정, 매핑, 화면 생성, CASE 검토 | 초안 저장·검토 요청 |
| 기획 리더 | 기준 버전·정책 충돌·화면 검토 | 기준정보와 산출물 승인 |
| 디자이너 | 구조 확정본에 시각 스타일 적용, 디자인 검토 | 디자인 결과 승인 |
| 개발자·QA | 동작·데이터 계약·테스트 확인 | 검증 결과 기록 |

- 열 이름이 "승인 권한 **제안**"이다. 확정 권한 체계가 아니다 (설계 §2 17행).
- "한 팀의 파일럿에서는 한 사람이 여러 역할을 수행할 수 있다. 다만 승인자·대상 버전·승인 시점은 남긴다." (설계 §2 24행)
- 개발프롬프트는 "제품 사용자는 기획자입니다" 로 못박는다 (개발프롬프트 9행).
- 전사 권한 체계는 후속 범위 (설계 §4 60행); 착수 기본값은 단일 팀 (설계 §15 303행).
- 축 A 가 시스템에 닿는 지점: 제품 API 의 "프로젝트 권한·입력 검증·버전 충돌 확인" (설계 §5 72행), `ChangeRequest / Decision / Approval` 의 "대상 버전, 요청·결정·이유·작성자, 승인 대상 hash" (설계 §6 106행), `POST /artifacts/:id/approvals` 의 "필수 검사·권한·버전 확인 후 승인" (설계 §13 276행).

### 2.2 축 B — 업무 사용자 역할이 등장하는 위치

| 단계·화면·엔터티 | 원문 표현 (역할 부분 강조) | 출처 |
|---|---|---|
| 1. 프로젝트 생성 | 서비스, 포털, **사용자 역할**, PC/모바일, 신규/개편, 목표·제외 범위 | 설계 §2 26행 |
| 6. 작업 입력 | 대상, 변경 목적, 참고 화면, 유지 조건, **역할·CASE** | 설계 §2 31행 |
| 제품 화면 '요구사항·정책' | 원문, 수용조건, **적용 역할·상태**, 충돌, 변경 영향 | 설계 §3 44행 |
| 엔터티 ScreenPlan / ScreenRevision | 내부 UUID, 기존 화면 ID, 별칭 이력, 목적, shell, 기기, **역할**, 명세 | 설계 §6 99행 |
| 프롬프트 폼 '대상' 구역 | 프로젝트, 기존 화면 ID, 포털, PC/모바일, **사용자 역할** | 설계 §8 144행 |
| 프롬프트 폼 'CASE' 구역 | 정상·빈값·오류·**권한**·처리중 등 적용 조건 | 설계 §8 148행 |
| 검증 V1 명세 | 스키마, 참조, **역할·상태**, 수용조건 연결 / 차단: 잘못된 구조, 필수 동작 미정 | 설계 §10 216행 |
| 수용 테스트 기록 ② | ①수용조건 ②**초기 상태·역할** ③사용자 동작 ④기대 결과 ⑤검증 artifact hash | 설계 §10 228행 |
| 첫 파일럿 과제 | 쉬운 문구·스타일 변경, 목록 검색·빈 상태, 글자수 제한, 뒤로가기, 팝업, **권한 차이** | 설계 §14 297행 |
| 작업 대화의 반복 문제 | 번호·설명 일치, 없는 버튼 설명 삭제, 다운로드 컬럼, 기본 정렬, **역할별 데이터 범위**, 이전 파일 참조 수정 | 보고서 §6 89행 |

흐름으로 보면 역할은 다음 경로로 전달된다.

```text
프로젝트 생성(사용자 역할 입력, §2 26행)
 → 작업 입력(역할·CASE, §2 31행) → 프롬프트 '대상'·'CASE'(§8 144·148행)
 → ScreenRevision 의 역할(§6 99행) → V1 '역할·상태' 검사(§10 216행)
 → 수용 테스트 ② 초기 상태·역할(§10 228행) → 파일럿 '권한 차이'(§14 297행)
```

### 2.3 포털이 놓인 위치 — 역할과 다른 엔터티

| 위치 | 원문 | 출처 |
|---|---|---|
| 프로젝트 생성 입력 | "포털" 과 "사용자 역할" 이 서로 다른 항목 (PC/모바일과도 별개) | 설계 §2 26행 |
| 제품 화면 'IA·화면 목록' | 계층·**포털**·기기, 기존 화면 ID, 경로, 구현·검증·승인 상태 | 설계 §3 45행 |
| 엔터티 Project | 프로젝트 UUID, 이름, **포털·기기 프로파일**, 권한 | 설계 §6 92행 |
| 엔터티 IANode | 부모, 명칭, 순서, **포털**, 화면 연결; 카테고리와 화면 구분 | 설계 §6 98행 |
| 프롬프트 폼 '대상' | 프로젝트, 기존 화면 ID, **포털**, PC/모바일, 사용자 역할 | 설계 §8 144행 |
| S2B 페이지 shell 규칙 | "**포털별** GNB/LNB 와 breadcrumb 규칙을 유지한다" | 설계 §9 201행 |
| INDEX 집계 | 1,428행 = 관리자 570, 수요기관 473, 공급업체 371, 공통 14 | 보고서 §3 44행 |

- 역할은 요구사항(§3 44행)과 ScreenRevision(§6 99행) 쪽 속성, 포털은 IA(§3 45행)·IANode(§6 98행)·Project 프로파일(§6 92행) 쪽 속성이다.
- 화면 검토 화면의 기능은 "HTML/명세/코드, PC·모바일, CASE 전환, 요소 번호, 검증 결과" 이며 역할 전환은 적혀 있지 않다 (설계 §3 48행). 권한 CASE 를 CASE 전환으로 본다면 역할 차이는 CASE 를 통해 보게 된다(제안, §5.4).
- 디자인 단계 입력은 `screen_revision_id`, `design_input_spec_hash`, 잠긴 요소·동작, 허용 토큰이며 역할·권한은 없다 (설계 §12 242행). 역할·권한 차이는 구조·동작 축이지 시각 축이 아니다.

### 2.4 원본에 없는 것

| 없는 것 | 확인 범위 | 의미 |
|---|---|---|
| 업무 사용자 역할의 값 목록 | 설계 전체(307행), 보고서 전체(100행), 개발프롬프트 전체(37행) | 프로젝트별 정의 대상. 시스템 enum 으로 고정할 근거 없음 |
| 포털의 값 목록 | 설계 본문에는 없음. 보고서 §3 44행 집계 라벨과 CSV `portal` 코드에만 있음 | S2B 프로파일의 데이터이지 제품 공통 enum 아님 (설계 §9 199·205행) |
| 역할 모델 엔터티 | 설계 §6 표에 `PolicyRevision / Term / StateModel` 은 있으나 RoleModel 류는 없음 | 역할 체계를 어디에 버전 관리할지 미정 (§6) |
| 권한 CASE 의 필수 여부 | 설계 §8 148행은 "정상·빈값·오류·권한·처리중 **등**" 예시 나열 | 필수 CASE 목록은 프로젝트·화면별 결정 (§6) |
| '역할별 데이터 범위' 의 구체 사례 | 보고서 §6 89행 키워드만; 카카오톡 원문은 저장소에 없음 (보고서 §1 27행, data/review/README) | 표현 방식(fixture vs 규칙) 미정 (§6) |

R21 은 상태 모델에 대한 규칙이다. 역할 체계에 같은 원칙을 적용하는 것은 **제안**이다(§5.1).

| 제품 사용자 축 | `Actor` 와 별도로 `product_role: enum(planner, lead, designer, dev_qa)` 선택 필드를 Approval/Decision/ValidationRun 작성자에 붙인다. `RoleId` 와 같은 필드·enum 에 넣지 않는다. 승인자·대상 버전·승인 시점은 필수 | R3, 설계 §6 106행, §13 276행 |
| 승인 권한 검사 | 단일 팀 기본값(설계 §15 303행)에서는 차단이 아니라 기록·경고로 시작한다. 전사 권한 체계는 후속(설계 §4 60행) | §6 Q7 |
| 요구사항 범위 | `RequirementRevision.scope` 자유 문자열을 `{ portal_id?, role_ids[], device? }` 구조 필드로 대체하거나 병기한다. 역할은 `applies_to_roles[]: { role_id, status: candidate \| adopted, evidence }` 로 사람이 채택 | R5, R8, §4.1 |

### 5.2 ScreenSpec·CASE

| 항목 | 제안 |
|---|---|
| `roles[]` | `ScreenRevision.roles` 와 필수성을 맞춘다. 비로그인·공통 화면을 위해 빈 배열 허용 여부는 Q4 로 남기고, 그때까지 `roles: []` + `unresolved(kind=question)` 조합으로 표현 |
| `states[].trace[]` | CASE 에 수용조건 trace 를 추가해 권한 CASE 를 요구사항에 직접 연결(fixtures README 의 우회 제거) |
| permission CASE | `case_kind=permission` 이면 `role` 필수, `role ∈ roles[]` |
| 요소·동작 단위 권한 차이 | `permission_rules[]: { role, target(element_id \| action_id), effect: hidden \| disabled \| enabled, trace[], evidence[] }`. 렌더러는 permission CASE 에서 적용. 비활성화/숨김 기본값은 원문이 정하지 않았으므로 프로파일 값(Q10) |
| 역할별 데이터 범위 | `states[].fixture_id` 를 역할별로 다르게 두고 더미데이터 fixture 에 `role`·`derived_from`·`filter` 를 기록(보고서 §6 89행). 실제 데이터 범위 규칙은 R11 에 따라 더미로만 표현 |
| 디자인 입력 | 역할·권한을 넣지 않는다(설계 §12 242행). 권한 차이가 구조 변경을 요구하면 화면명세 변경 요청으로 되돌린다(설계 §12 244행) |

### 5.5 수입기·기준정리 화면 (설계 §3 44행 '적용 역할·상태')

- 요구사항 description 의 주체 키워드는 `applies_to_roles` **후보**(status=candidate, evidence=SourceAnchor)로만 제시하고 기획자가 채택한다(R8). 키워드가 없는 213행은 '역할 미지정' 으로 남긴다.
- ❍ 머리표는 SourceAnchor locator 의 절 구조로 파싱하되 역할로 해석하지 않는다(§4.3).
- INDEX 수입기는 CSV 의 `portal` 코드를 그대로 쓰고 href 최상위 디렉터리·id 접두어로 포털을 재추론하지 않는다. _공통 하위 demand 6·supplier 4행은 portal 코드를 유지한 채 디렉터리만 별도 필드로 기록한다(§4.5).

### 5.6 프롬프트·API

- 프롬프트 문맥(설계 §8)에 대상 역할의 정의(label, description, allowed_portals, evidence)와 `permission_rules` 초안을 포함한다. 모델 출력의 `roles`·`states[].role` 은 서버가 `Project.roles` 와 대조해 재검사한다(R9).
- 프롬프트 계약의 "외부 ID·상태값·정책을 임의 변경하지 않는다"(R10)에 "역할 ID 를 임의 생성하지 않는다" 를 추가한다.
- API: `POST /projects/:id/...` 는 프로젝트 권한(축 A)을 확인한다(설계 §5 72행). `POST /artifacts/:id/approvals` 는 필수 검사·권한·버전 확인 후 승인(설계 §13 276행). 축 B(업무 역할)는 API 권한이 아니라 화면명세의 데이터다.

### 5.7 CLAUDE.md 에 넣을 규칙 문장(제안)

> 포털과 사용자 역할은 별개 축이다. 포털 코드(admin/demand/supplier/front)·디렉터리명·파일명 접두어를 역할로 쓰지 않는다. 역할 목록은 프로젝트 프로파일에서 오며 원문 확정 전에는 unresolved/합성 값으로 둔다. 제품 사용자 역할(기획자·기획 리더·디자이너·개발자·QA)은 승인·기록 축이며 RoleId 와 섞지 않는다. 권한 CASE 는 role 과 fixture 를 가져야 하고, 역할 검사가 구현되지 않은 동안 not_run 으로 표시한다. 요구사항 본문의 ❍ 머리표는 절 제목이며 역할 추출에 쓰지 않는다.
