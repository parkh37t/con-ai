# 01. 제품 정의와 사용 흐름

기획자가 브라우저에서 요구사항정의서·IA·정책·AS-IS 자료를 등록하고, 요구사항(수용조건 단위)과 화면의 다대다 관계를 확정한 뒤, 표준 프롬프트 폼으로 화면명세와 동작하는 HTML 목업을 생성·검증·승인·내보내는 워크스페이스를 정의한다. 출처 범위: 설계 §1~§4(제품 정의·사용자·흐름·화면·MVP)와 §8·§11·§14·§15 일부, 보고서 §1~§3·§6, 개발프롬프트 전체, `data/review` CSV·JSON 실측.

관점: 제품 정의 · 사용자/역할/승인 권한 · 9단계 사용 흐름 · 9개 제품 화면 · 생성 작업 유형 5종과 MVP 우선순위 · MVP 포함/후속 범위 · 1,603개 HTML 이관 원칙.

이 문서가 다루지 않는 것: 데이터 모델·ID·버전(`02`), 매핑·커버리지·충돌(`03`), 프롬프트 문맥·AI 어댑터(`04`), 명세→HTML 계약(`05`), 검증·승인 파이프라인(`06`), 시스템 구조·개발 순서(`07`), 업무 사용자 역할(수요기관·공급업체 등)과 제품 사용자 역할의 분리(`10`, 별도 검증 중).

## 2. 핵심 개념·흐름

### 2.1 제품 정의 (설계 §1)

| 항목 | 내용 | 출처 |
|---|---|---|
| 정의 | 기획자가 브라우저에서 요구사항정의서·IA·정책·AS-IS 분석서를 등록하고, 요구사항과 화면의 관계를 확정한 뒤, 표준 프롬프트로 화면명세와 동작하는 HTML 목업을 만드는 워크스페이스 | 설계 §1 |
| 보존 대상 3가지 | 왜 이 화면을 만들었는지 / 어떤 요구사항을 어디에서 충족하는지 / 무엇을 검증했는지 | 설계 §1 |
| Claude Code의 위치 | 이 제품의 **개발 도구**다. 운영 중 사용자 요청을 처리하는 AI 호출은 서버의 모델 어댑터로 분리한다 | 설계 §1; 개발프롬프트 |
| 시작 구조 | 브라우저에서 개발용 Claude Code 세션을 직접 실행시키는 구조로 시작하지 않는다 — 이 문장은 설계에만 있고 개발프롬프트에는 앞 두 문장만 있다 | 설계 §1 |
| 재사용 대상 | BNK 콘솔의 작업 선택·프롬프트·미리보기 UX / S2B의 화면·설명 규격 / APEX의 단계별 검토 개념 | 설계 §1 |
| 별도 데이터·상태로 관리 | BNK의 성공 표시 ≠ 실제 검증, INDEX 등록 ≠ 구현 완료, HTML의 REQ 문자열 ≠ 승인된 매핑 | 설계 §1 |
| 원본 내 지시문 | 실행·위임 지시는 참고 자료로만 취급한다 | 설계 §1; 개발프롬프트 |

### 2.2 사용자 4종과 승인 권한 제안 (설계 §2 표)

열 제목이 "승인 권한 **제안**"이다. 확정 권한 모델이 아니다.

| 사용자 | 주 작업 | 승인 권한 제안 |
|---|---|---|
| 기획자 | 자료 등록, 추출 정정, 매핑, 화면 생성, CASE 검토 | 초안 저장·검토 요청 |
| 기획 리더 | 기준 버전·정책 충돌·화면 검토 | 기준정보와 산출물 승인 |
| 디자이너 | 구조 확정본에 시각 스타일 적용, 디자인 검토 | 디자인 결과 승인 |
| 개발자·QA | 동작·데이터 계약·테스트 확인 | 검증 결과 기록 |

- 한 팀의 파일럿에서는 한 사람이 여러 역할을 수행할 수 있다. 다만 **승인자·대상 버전·승인 시점**은 남긴다 (설계 §2).
- 개발프롬프트는 "제품 사용자는 기획자"로 정의한다. 브라우저에서 요구사항·IA·정책을 확인하고 요구사항 ID와 화면기획 ID를 연결한 후, 표준 입력 폼으로 화면명세와 HTML 목업을 생성·수정·검토·내보낸다 (개발프롬프트).
- 착수 기본값은 "단일 팀"이며 "전사 권한 체계"는 후속이다 (설계 §15, §4).
- 여기의 역할은 **제품 사용자 역할**이다. 프로젝트 생성 입력의 "사용자 역할", 프롬프트 대상 구역의 "사용자 역할", CASE의 "권한"은 **업무 사용자 역할(화면 이용자)** 축이며 별개다 (설계 §2, §8). 두 축의 관계는 `10_사용자_역할의_두_축_분리` 문서가 다룬다.
- 디자이너의 작업은 MVP 이후 단계 연계 대상이다. MVP는 HTML 기획 목업까지 완성한다 (설계 §12).

### 2.3 9단계 사용 흐름 (설계 §2)

| # | 단계 | 사용자가 하는 일 | 보존·분리 대상 | 주 사용 화면 (제안) |
|---|---|---|---|---|
| 1 | 프로젝트 생성 | 서비스, 포털, 사용자 역할, PC/모바일, 신규/개편, 목표·제외 범위 입력 | — | 프로젝트 홈 |
| 2 | 자료 등록 | 원본 파일을 버전별 보관, 유형별로 읽음. 원문과 추출값을 나란히 확인 | 원본 버전(SHA256), 원문 위치 | 자료·기준정보 |
| 3 | 기준 정리 | 요구사항·정책·IA·용어·상태값의 중복·충돌 해결 | 미확정은 **별도 목록** | 자료·기준정보, 요구사항·정책 |
| 4 | 화면 목록 구성 | 기존 화면 ID와 파일 경로 수입 | 충돌·유실 경로는 **검토 대상으로 분리** | IA·화면 목록 |
| 5 | 매핑 확정 | 요구사항의 **수용조건 단위**로 화면·동작·비화면 작업 연결 | 다대다 관계, 근거 | 매핑 작업대 |
| 6 | 작업 입력 | 대상, 변경 목적, 참고 화면, 유지 조건, 역할·CASE 입력 | — | 생성 작업대 |
| 7 | 화면명세 생성 | AI 제안과 근거·미확정 항목을 검토한 뒤 명세 버전 확정 | 명세 버전 | 생성 작업대, 화면 검토 |
| 8 | HTML 생성·검증 | **동일 명세**에서 UI와 우측 설명 생성. 자동 검사 + 사람 검토 | 검증 결과 | 화면 검토 |
| 9 | 수정·승인·배포용 내보내기 | 변경 차이·영향 범위 확인. HTML·명세·매핑·검증 결과를 **함께** 내려받음 | 승인 hash, 변경 이력 | 변경·이슈, 승인·내보내기 |

"주 사용 화면" 열은 설계 §2와 §3을 대응시킨 제안이다. 원문은 단계와 화면을 직접 연결하지 않는다.

입력 원칙: 기획자는 **화면 목적과 변경 의도**를 입력한다. 모델 이름·토큰 수·내부 JSON 등은 기본 입력 화면에서 숨기고 필요한 상세 보기에서 제공한다 (설계 §2).

### 2.4 제품 화면 9개와 필요한 기능 (설계 §3)

설계 §3 표의 열 제목은 "제품 화면 | **필요한 기능**"이다. 항목은 "보여야 할 데이터"가 아니라 기능이며, 원문은 표시 데이터와 사용자 동작을 구분하지 않는다(예: "채택/보류", "기준 버전 확정", "CASE 전환", "오프라인 ZIP"은 동작에 가깝다). 아래 "읽는 엔터티" 열은 설계 §6 표와 대응시킨 제안이다.

| 제품 화면 | 필요한 기능 (원문) | 읽는 엔터티 (제안, 설계 §6) |
|---|---|---|
| 프로젝트 홈 | 진행 단계, 미해결 충돌, 검토 대기, 실패 작업, 최근 승인본 | Project, TraceLink(conflict), Artifact(review_ready/approved), GenerationJob(failed) |
| 자료·기준정보 | 파일 버전, 원문 위치, 추출 결과, 채택/보류, 기준 버전 확정 | SourceDocument/SourceVersion, SourceAnchor, Baseline |
| 요구사항·정책 | 원문, 수용조건, 적용 역할·상태, 충돌, 변경 영향 | Requirement/RequirementRevision, AcceptanceCriterion, PolicyRevision/Term/StateModel |
| IA·화면 목록 | 계층·포털·기기, 기존 화면 ID, 경로, 구현·검증·승인 상태 | IANode, ScreenPlan/ScreenRevision, Artifact, ValidationResult, TraceLink |
| 매핑 작업대 | 요구사항↔화면 다대다 연결, 수용조건별 근거, 누락·과잉 연결 | TraceLink, AcceptanceCriterion, NonUIScreenWork |
| 생성 작업대 | 작업 유형, 대상·변경·유지 조건, 참고 화면, 자동 프롬프트, 실행 이력 | GenerationJob, PromptTemplate, Baseline |
| 화면 검토 | HTML/명세/코드, PC·모바일, CASE 전환, 요소 번호, 검증 결과 | Artifact, ScreenSpec, ValidationRun/ValidationResult |
| 변경·이슈 | 버전에 고정된 코멘트, 해결 결정, 영향 화면, 전후 비교 | ChangeRequest/Decision, TraceLink |
| 승인·내보내기 | 승인 대상 묶음, 미해결 차단 항목, 변경 이력, 오프라인 ZIP | Approval, ValidationResult, Artifact |

IA·화면 목록의 "구현·검증·승인 상태"는 하나의 값이 아니라 세 판정이다. 판정 원칙은 설계 §7 표에 있다.

| 항목 | 판정 원칙 (설계 §7) |
|---|---|
| 매핑 후보 | HTML 토큰·IA·유사도 기반 추출; 아직 미승인 |
| 승인 매핑 | 동일 기준 버전에서 담당자가 의미·범위를 확인 |
| 화면 구현 | 관련 요소·상태·동작이 해당 artifact에 존재 |
| 검증 완료 | 연결된 수용조건 테스트가 해당 artifact에서 통과 |
| 제외·비UI | 사유와 별도 책임·검증 연결이 있어야 함 |

"자동 프롬프트"는 표시 데이터가 아니라 서버가 버전이 있는 템플릿으로 조립하는 기능이다 (설계 §8). 화면 검토의 "요소 번호"는 화면 숫자·설명 숫자·영역 내 a/b/c 표시를 동일 데이터에서 만들고, 내부 요소 UUID와 표시 번호를 구분한다 (설계 §9).

### 2.5 생성 작업 유형 5종과 MVP 우선순위 (설계 §3; 보고서 §2)

| 작업 유형 (BNK) | MVP | 비고 | 코드 초안 enum (`packages/schemas/src/job.ts`) |
|---|---|---|---|
| 신규 생성 | 포함 | — | `create` |
| 단건 수정 | 포함 | 수정은 검증 가능한 변경 집합 (설계 §9) | `edit` |
| 참조 복제 | 포함 | golden 화면의 승인 버전을 참고 (설계 §8) | `clone_reference` |
| 페이지→팝업 | 후순위 | shell 변환과 접근성 재검사 필요 | `page_to_popup` |
| 구조적 재생성 | 후순위 | 영향 범위가 넓음 | `structural_regenerate` |

생성 작업대의 입력 폼은 7구역이며 서버가 버전이 있는 템플릿으로 조립한다 (설계 §8).

| 구역 | 입력 |
|---|---|
| 대상 | 프로젝트, 기존 화면 ID, 포털, PC/모바일, 사용자 역할 |
| 작업 | 신규/수정/참조 복제, 목적, 변경 범위 |
| 기준 | baseline ID, 승인 REQ·수용조건, 정책·IA·용어 |
| 참고 | golden 화면의 승인 버전, shell, 디자인 토큰 |
| CASE | 정상·빈값·오류·권한·처리중 등 적용 조건 |
| 유지 조건 | 변경 금지 요소, 데이터 계약, 유지할 동작 |
| 산출 | 화면명세 JSON, 근거 연결, 질문·가정·충돌 |

BNK에서 가져오는 것과 새로 만드는 것 (보고서 §2):

| 구분 | 항목 |
|---|---|
| 재사용 (UX) | 대상 선택, 변경 목적·유지 조건, 문맥 표시, 참고 화면, CASE·기기 미리보기, 다운로드 |
| 새로 구현 | 모델 호출, 결과 저장, 실제 검증, 수정 이력, 버전 충돌, 승인과 실패 처리 |
| 채택하지 않음 | BNK 데모의 모델 선택지 이름 (설계 §8) |

BNK 원본 3종의 판단 (보고서 §1, §2):

| 원본 | 확인 내용 | 설계 반영 |

### 2.6 MVP 범위 (설계 §4)

| 구분 | 항목 |
|---|---|
| 포함 | 프로젝트 관리, MD·CSV·XLSX 요구사항 입력, 기존 HTML 참고 등록, 선택한 S2B INDEX 수입, 기준정보 정정, 다대다 매핑, 구조화 프롬프트, 화면명세, 정해진 컴포넌트의 HTML 생성, CASE·더미데이터, 자동 검사, 사람 검토, 버전·승인·ZIP 내보내기 |
| 후속 | 모든 형식의 범용 ZIP 이관, HWP·PDF OCR, 임의 웹사이트 AS-IS 자동 분석, Figma 쓰기 연동, 자유형 HTML/JS 생성, 실시간 공동편집, 전사 권한 체계, 디자인 변형의 대규모 자동화 |

- XLSX는 이번 자료의 요구사항 원장이므로 MVP에 포함한다. 범용 자동 추론 대신 **시트·헤더·ID 열을 확인하는 가져오기 설정**을 두고, 현재 S2B 원장의 SFR 시트 A열처럼 프로젝트별 규칙을 저장한다 (설계 §4). 시트 전체 정규식 검색은 부모 RFP 등의 ID까지 잡으므로 지정된 ID 열을 기준으로 한다 (보고서 §3).
- 초기 AS-IS는 기획자가 정리한 MD/CSV와 선택 화면을 근거로 등록한다 (설계 §4).
- "정해진 컴포넌트의 HTML 생성": 렌더러는 승인된 컴포넌트와 제한된 동작 목록만 쓴다. 검색은 더미데이터 필터, 정렬은 명세의 기본 정렬, 팝업은 지정된 전이, 다운로드는 명세에 정의된 컬럼의 예제 파일. 실제 거래·개인정보 조회·외부 업무 API는 연결하지 않는다 (설계 §9).
- "기존 HTML 참고 등록"으로 올린 HTML과 문서 내용은 근거 데이터이며 시스템 지시나 실행 코드가 아니다. 원본 HTML의 스크립트는 서버에서 실행하지 않는다 (설계 §5).
- 오프라인 ZIP은 HTML, 로컬 CSS/JS/폰트·이미지, fixture, 명세, 매핑표, 검증 보고서, manifest를 포함한다 (설계 §9).

**1,603개 HTML 이관 원칙** (설계 §4): 한 번에 새 명세로 전환하지 않는다.

```text
원본 보존 → 목록 점검 → 대표 화면 선정 → 명세 역추출 → 사람 확인 → 템플릿 등록
```

- 파일명·화면 ID 변경은 별칭 이력과 경로 이동 기록을 남기는 명시적 변경 작업이다. 과거 승인본은 당시 ID를 유지한다 (설계 §6).
- 기존 golden은 검증을 거쳐 승인할 템플릿 후보이지 모든 의미가 검증된 정답이 아니다 (보고서 §4).
- 첫 파일럿은 쉬운 문구·스타일 변경, 목록 검색·빈 상태, 글자수 제한, 뒤로가기, 팝업, 권한 차이를 포함하고, 100장 이상 대규모 과제는 제외한다 (설계 §14).

### 2.7 개발프롬프트의 착수 정의

착수 순서: 저장소 상태와 실행 환경 확인 → 설계의 단계 1~2에 해당하는 기반부터 구현. 기존 앱이 있으면 구조를 조사해 존중한다. 처음부터 12개 자율 에이전트를 만드는 대신 단계별 입력·출력이 있는 워크플로를 만든다 (개발프롬프트; 설계 §5).

| 단계 (설계 §14) | 작업 | 완료 기준 |
|---|---|---|
| 0 | 대표 화면·원장·충돌 기준 선정 | 10~20개 후보와 검증할 업무 조건 합의 |
| 1 | 자료·ID·버전·매핑 기반 | XLSX 정확한 열 추출, 중복·충돌 보존, 근거 표시 |
| 2 | AI 없는 화면명세·렌더러 | 목록·상세·팝업 및 설명이 같은 명세에서 생성 |

첫 구현 범위 6개 (개발프롬프트). 조건문이 완료 조건이므로 함께 적는다.

| # | 범위 | 붙어 있는 조건 |
|---|---|---|
| 1 | 프로젝트·원본 버전·근거 위치·요구사항·수용조건·화면 버전·매핑 모델 정의 | 내부 UUID와 사용자가 보는 기존 외부 ID를 분리 |
| 2 | SFR 시트의 ID 열을 지정해 XLSX 수입 | 원문 위치 보존. 동봉 444개 CSV와 비교. 중복 ID·경로·의미 충돌은 검토 대상으로 남김 |
| 3 | 합성 데이터로 목록 화면 하나를 명세 JSON에서 렌더링 | UI와 우측 설명을 같은 명세에서 생성. 검색·빈 결과·오류 CASE 지원 |
| 4 | 수용조건을 요소·동작에 연결하는 매핑 화면과 근거 표시 | 토큰이 발견됐다는 이유로 승인 처리하지 않음 |
| 5 | 구조·참조·CASE 검증, 결과 pass/fail/error/not_run | 실제로 실행하지 않은 검사는 통과 표시하지 않음 |
| 6 | 실제 AI 명세 생성, 단건 수정, 버전 비교, 승인·내보내기를 단계적으로 연결 | — |

- 첫 수용조건: "원문에서 가져온 요구사항 하나를 화면 요소·CASE에 연결하고, 같은 명세로 HTML과 설명을 만든 뒤, 일부러 잘못된 매핑·누락 CASE를 넣으면 검증이 실패하는 것". 시각적 데모의 성공 표시만으로 완료 처리하지 않는다 (개발프롬프트).
- 착수 시 고정할 기본값: 단일 팀, 기존 화면 ID 유지, 수용조건 단위 추적, 명세 우선 생성, S2B 프로파일 분리, 실제 검증 기반 승인 (설계 §15).
- 담당 기획자가 결정할 항목: 충돌하는 REQ의 정본, 중복 화면 ID의 실제 화면 구분, 52개 경로의 이동·폐기 여부, 미확정 정책·상태값, 승인할 golden 버전. 해결 전에도 합성 데이터와 확인된 대표 화면으로 개발은 진행한다 (설계 §15; 개발프롬프트).

### 5.3 검증·테스트

- 첫 수용조건용 fixture 3종: REQ-SFR-066-001 충돌, REQ-SFR-038-001 UI/비UI 분할, 잘못된 매핑·누락 CASE 실패 예제. 저장소 `fixtures/`에 이미 있다 (개발프롬프트; 설계 §7).
- 데모(저장 HTML 표시)와 실제 생성(프롬프트→새 결과)을 수용 테스트에서 구분한다. 타이머 기반 성공 표시는 작업 성공이 아니다 (보고서 §2). `packages/domain`의 작업 전이표는 `queued → succeeded`를 거부한다.
- 새로고침 후 작업·검증 결과 유지: 클라이언트는 재접속 시 서버 상태를 다시 읽는다 (설계 §11).
- 수용 테스트는 ①수용조건 ②초기 상태·역할 ③사용자 동작 ④기대 결과 ⑤검증 artifact hash를 기록한다. 콘솔 오류 0개나 CASE 버튼 개수로 대신하지 않는다 (설계 §10).
- 파일럿 측정은 생성 시간뿐 아니라 원문 확인·정정·검토·수정 시간을 포함하고, 승인된 수용조건 충족률·검토 후 재발 결함·무관 변경·생성 실패율·화면당 모델 비용을 기록한다 (설계 §14).
