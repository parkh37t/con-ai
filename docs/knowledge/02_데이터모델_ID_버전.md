# 02. 데이터 모델·ID 분리·버전 원칙

**요약** — 설계 §6 은 Project 부터 ChangeRequest/Decision/Approval 까지 15 개 엔터티 묶음을 정의하고, 원본 불변·엔터티별 버전·기준 버전(baseline) 고정과 `검토 필요` 표시·내부 UUID 와 외부 화면 ID 분리·별칭 이력과 경로 이동 기록·중복 수입의 임시 레코드를 원칙으로 둔다. 설계 §11 은 작업 상태(queued → running → succeeded / failed / cancelled)와 산출물 상태(draft → validation_pending → review_ready → approved, 변경 시 새 draft 또는 stale)를 독립으로 관리한다.

**출처 범위** — 설계 §6·§11(중심), §2·§4·§5·§7·§8·§9·§10·§12·§13·§15(관련 문장); 보고서 §1·§3·§4·§5·§6·§7; 개발프롬프트(첫 구현 범위 1·2, 반드시 지킬 규칙). 실측은 `data/review/` 의 INDEX 레지스트리·경로확인 52건·요구사항 원문추출·HTML REQ 추적후보 CSV 와 `집계기준_결과.json`(설명: `data/review/README.md`). 코드 대조는 `packages/schemas`, `packages/domain`, `fixtures`. 원본 문서는 `docs/reference/` 에 있으며 이 문서는 요약·정리다.

## 2. 핵심 개념·흐름

### 2.1 엔터티 (설계 §6 표)

| 엔터티 | 주요 필드·관계 (설계 §6) | 코드 초안 위치 (`packages/schemas/src`) |

| IANode | 부모, 명칭, 순서, 포털, 화면 연결; 카테고리와 화면 구분 | `screen.ts` |
| ScreenPlan / ScreenRevision | 내부 UUID, 기존 화면 ID, 별칭 이력, 목적, shell, 기기, 역할, 명세 | `screen.ts` |
| TraceLink | 기준 버전, 요구사항 수용조건, 화면 버전, 요소/동작, 근거, 제안·승인 상태 | `trace-link.ts` |
| NonUIScreenWork | 배치·연계·권한 서비스 등, 수용조건 연결, 담당·검증 근거 | `screen.ts` |

| PromptTemplate / GenerationJob | 템플릿 버전, 입력 스냅샷, 모델 설정, 실행 상태, 비용·시간 | `job.ts` |

관련 원칙: BNK 의 성공 표시·INDEX 등록·HTML 의 REQ 문자열은 각각 "실제 검증"·"구현 완료"·"승인된 매핑"이 아니며 별도 데이터와 상태로 관리한다 (설계 §1). IA·화면 목록 화면은 계층·포털·기기, 기존 화면 ID, 경로, 구현·검증·승인 상태를 보여준다 (설계 §3). 즉 화면 하나의 상태는 최소 구현/검증/승인 세 축이다.

### 2.2 세 층의 식별자

| 식별자 | 무엇 | 규칙 | 출처 |
|---|---|---|---|
| 내부 UUID | 시스템이 부여하는 불변 키. Requirement, ScreenPlan, 화면 요소에 각각 둔다 | 내부 관계는 UUID 로 보존한다. 원장의 행 순서에 의존한 외부 번호가 바뀌어도 관계는 유지된다 | 설계 §6, §9 |
| 외부 화면 ID (기존 화면 ID) | 사용자에게 익숙한 S2B 파일명 기반 ID. INDEX 의 `id` | 우선 표시한다. 프로젝트 내 현재 값은 유일. 새 `SP-...` 번호를 기존 ID 대신 강제하지 않는다 | 설계 §6; 개발프롬프트 규칙 |
| 외부 REQ ID | 요구사항 원장 SFR 시트 지정 열의 `REQ-SFR-NNN-NNN` | 지정 ID 열 기준으로 수입한다(시트 전체 정규식은 부모 ID 까지 526 개를 잡는다). 임의 생성·대체하지 않는다 | 보고서 §3; 설계 §7 |
| 표시 번호 (a/b/c) | 화면·설명의 영역 안 요소 번호 | 영역마다 반복되는 a 는 전역 중복 오류가 아니다. 내부 요소 UUID 와 구분한다 | 설계 §9 |
| 로컬 ID (코드 초안) | 화면명세 안 영역·요소·동작·CASE 의 ID (`common.ts` `LocalId`) | 명세 안에서만 유효. 설계에는 별도 이름이 없다 — 코드가 이름을 붙인 것 | `packages/schemas` |

디자인 단계로는 `screen_revision_id` 와 `design_input_spec_hash` 를 키로 전달하고, 디자인에서 새 화면 ID 를 임의 부여하지 않는다 (설계 §12).

### 2.3 버전 원칙 (설계 §6)

| 원칙 | 내용 | 출처 |
|---|---|---|
| 원본 불변 | 원본은 덮어쓰지 않는다. SourceVersion 이 SHA256 으로 파일 내용 하나에 고정된다 | 설계 §6 |
| 엔터티별 버전 | 수용조건·매핑·화면명세·HTML 은 각각 버전이 있다. 승인본도 수정 시 새 버전을 만든다 | 설계 §6 |
| 기준 버전 고정 | 생성 작업은 사용한 기준 버전을 고정한다. 도중에 정책이 바뀌어도 결과의 근거가 섞이지 않는다 | 설계 §6 |
| `검토 필요` | 생성 완료 시 최신 기준과 달라졌으면 `검토 필요` 로 표시한다 | 설계 §6 |
| 당시 ID 유지 | 과거 승인본은 당시 ID 를 유지한다 | 설계 §6 |
| hash ≠ 내용 동일성 | 원본백업 PPTX 는 추출 텍스트가 같아도 파일 hash 가 다르다. SHA256 유일성은 내용 동일성 판정이 아니다 | 보고서 §1 |
| 기존 HTML 전환 순서 | 1,603 개 HTML 을 한 번에 전환하지 않는다. 원본 보존 → 목록 점검 → 대표 화면 선정 → 명세 역추출 → 사람 확인 → 템플릿 등록 | 설계 §4 |

### 2.4 외부 화면 ID·별칭 이력·임시 레코드 흐름

```text
INDEX 수입 (설계 §2 4단계: 기존 화면 ID 와 파일 경로를 수입)
 → 행 분류
    ├─ 유일 ID + 경로 확인            → 공식 레지스트리 등록 후보
    ├─ 같은 ID 가 여러 행/기존 레코드   → 임시 레코드 (경로가 같아도 자동 병합 금지)
    ├─ 경로 미확인                    → 임시 레코드 (같은 파일명 후보는 연결 후보일 뿐)
    └─ 과거 별칭과 같은 ID             → 검토 대상 (이름 하나로 자동 별칭 금지)
 → 담당 기획자 결정 (설계 §15: 중복 화면 ID 의 실제 화면 구분, 52 개 경로의 이동·폐기 여부)
 → 별칭 이력 + 경로 이동 기록을 남기는 명시적 변경 작업 (설계 §6)
 → 공식 레지스트리 승격
```

| 단계 | 규칙 | 출처 |
|---|---|---|
| 수입 | 충돌·유실 경로는 검토 대상으로 분리한다 | 설계 §2 |
| 중복 | 중복 수입은 별도 임시 레코드로 받아 해결 전 공식 레지스트리에 합치지 않는다 | 설계 §6 |
| 중복 | 중복 ID 중 서로 다른 경로 그룹(32)은 자동 병합하지 않는다 | 보고서 §3 |
| 경로 유실 | 52 건은 현재 ZIP 에서 경로가 맞지 않는다는 뜻이지 새로 제작할 52 건이 아니다. 같은 파일명 후보도 내용·포털·승인 버전 확인 후 연결한다 | 보고서 §3 |
| 별칭 | 폐기 ID 이력도 중복될 수 있으므로(IS005 가 서로 다른 명칭으로 등장) 이름 하나로 자동 별칭을 만들지 않는다 | 보고서 §4 |
| 개명 | 파일명·화면 ID 변경은 별칭 이력과 경로 이동 기록을 남기는 명시적 변경 작업이다. 일괄 치환보다 대상·경로·원장 변경을 묶는 명시적 이관 기능이 필요하다 | 설계 §6; 보고서 §5 |
| 수입 설정 | XLSX 가져오기 설정(시트·헤더·ID 열)을 프로젝트별 규칙으로 저장한다. 수입 설정 자체가 데이터 모델의 일부다 | 설계 §4, §14 |

| 항목 | 내용 | 출처 |
|---|---|---|
| 정의 | 채택한 자료·요구사항·정책·화면·템플릿의 정확한 버전 묶음 | 설계 §6 |
| 고정 API | `POST /projects/:id/baselines` — 채택된 자료·정책 버전 고정 | 설계 §13 |
| 사용처 | 프롬프트 기준 구역의 baseline ID, ScreenSpec 의 `baseline_id`, TraceLink 의 기준 버전, GenerationJob 이 고정하는 기준 | 설계 §8, §9, §6 |
| 문맥 우선순위 | 사람이 확정한 현재 baseline·결정 > 해당 범위의 채택된 정책/요구사항 > 승인 템플릿 > 참고 HTML. 원문 충돌은 날짜만 보고 자동 채택하지 않고 빠진 근거는 `unresolved` 로 내보낸다 | 설계 §8 |
| 승인 매핑 조건 | 동일 기준 버전에서 담당자가 의미·범위를 확인 | 설계 §7 |
| 상태값 채택 | 서로 다른 출처의 상태 체계를 같은 enum 으로 합치지 않고 적용 범위·채택 버전을 사람이 정한다 | 보고서 §4 |

### 2.6 작업 상태와 산출물 상태 (설계 §11)

| 체계 | 값 | 비고 | 출처 |
|---|---|---|---|
| 작업 상태 | queued → running → succeeded / failed / cancelled | 작업 성공과 산출물 승인 상태는 독립이다 | 설계 §11 |
| 산출물 상태 | draft → validation_pending → review_ready → approved | 변경 발생 시 새 draft 또는 stale 로 관리한다 | 설계 §11 |
| 검사 결과 | pass / fail / error / not_run | 생명주기가 아닌 결과값. 위 두 체계와 합치지 않는다 | 설계 §10; 보고서 §4 |
| 매핑 상태 | 제안·승인·conflict·제외·비UI (전체 enum 은 미확정) | TraceLink 의 상태 | 설계 §6, §7 |

작업 레코드에는 idempotency key, 입력 버전, 진행 단계, 제한 시간, 취소 요청을 둔다 (설계 §11). 재시도는 허용 범위가 정해져 있다: 일시적인 모델 오류는 제한 횟수 재시도하고 스키마 실패는 구체 오류를 전달해 제한적으로 보정한다. 무한 자동 수정은 하지 않는다 (설계 §11). MVP 작업 큐는 DB 기반 lease 와 재시도 정책으로 시작할 수 있다 (설계 §5). 클라이언트는 진행 이벤트를 받더라도 재접속 시 서버 상태를 다시 읽고, 새로고침 이후에도 작업·검증 결과가 유지되어야 한다 (설계 §11; 개발프롬프트 규칙).

코드 초안(`packages/domain/src/state-machines.ts`)의 전이표는 설계에 없는 역방향 전이를 해석으로 추가했다 — validation_pending → draft(필수 검사 실패), review_ready → validation_pending(재검증), approved → stale 만 허용, stale 은 종료 상태. 설계는 정방향만 적었으므로 이 해석은 §6 미확정 항목이다.

### 2.7 hash·revision·승인 연결

| 규칙 | 출처 |
|---|---|
| Artifact 는 content hash 를 가지며 ValidationRun/ValidationResult 는 artifact hash 에, Approval 은 승인 대상 hash 에 고정된다 | 설계 §6 |
| 승인은 정확한 artifact hash 에 연결한다. 필수 검증이 실패·오류·미실행이면 승인할 수 없다 | 개발프롬프트 규칙; 설계 §10 (`error`·`not_run`) |
| 승인자·대상 버전·승인 시점을 남긴다 (한 사람이 여러 역할을 맡더라도) | 설계 §2 |
| `POST /artifacts/:id/validations` 는 해당 hash 의 검증 실행, `POST /artifacts/:id/approvals` 는 필수 검사·권한·버전 확인 후 승인, `POST /projects/:id/exports` 는 승인 버전 묶음의 내보내기 | 설계 §13 |
| 동시 편집은 revision 기반 충돌 검사로 오래된 저장을 차단한다. `PATCH /trace-links/:id` 는 revision 필수 | 설계 §11, §13 |
| 프롬프트 템플릿·모델 식별자·입력 hash·원문 anchor·생성 결과를 기록한다 | 설계 §8 |
| 수용 테스트는 ①수용조건 ②초기 상태·역할 ③사용자 동작 ④기대 결과 ⑤검증 artifact hash 를 기록한다 | 설계 §10 |
| 기존 검증 코드에는 예외 시 종료코드 0 경로가 있으므로 실행 오류를 별도 상태(`error`)로 보존한다 | 보고서 §5 |

### 2.8 변경 영향과 ChangeRequest (설계 §11, §12)

1. 요구사항·정책 변경 시 TraceLink 로 영향 화면·명세·테스트를 찾고 기존 승인을 stale 로 표시한다 (설계 §11).
2. 사람이 변경 영향 범위를 확인한 뒤 재생성한다 (설계 §11).
3. 카카오톡·코멘트 기반 요청은 ChangeRequest 로 정리하고, 파일명뿐 아니라 artifact hash·요소 ID·CASE 에 고정한다 (설계 §11). 보고서 §6 은 작업 대화에서 반복되는 문제(번호·설명 불일치, 이전 파일 참조 수정 등)를 근거로 변경 요청에 대상 버전·요소·CASE 와 해결 결정을 붙이는 기능을 MVP 에 포함하라고 한다.
4. 수정은 전체 재생성 대신 기존 명세에 검증 가능한 변경 집합을 적용하고 잠긴 요소·무관한 화면의 변화를 검사한다 (설계 §9). 고정된 명세·렌더러·자산 버전에서 같은 HTML 을 재현할 수 있어야 하지만, AI 명세 작성 자체의 반복 결과까지 동일하다고 보장하지는 않는다 (설계 §9).
5. 디자인 단계는 색·폰트·간격 변경과 구조·동작 변경을 구분하며, 구조 변경이 필요하면 화면명세 변경 요청으로 되돌린다 (설계 §12).

### 5.3 검증·테스트

- 회귀 테스트 assertion 은 실측 수치를 그대로 쓴다: INDEX 1,428 행 ≠ 화면 수(고유 id 1,385·고유 href 1,410·중복 그룹 43/18·미확인 52·후보 43), 요구사항 444/444·row 8~451·그룹 83, 추적후보 1,212/937 (개발프롬프트 첫 구현 범위 2: 444 개 CSV 로 비교).
- 첫 수용조건은 "요구사항 하나를 화면 요소·CASE 에 연결하고, 같은 명세로 HTML 과 설명을 만든 뒤, 일부러 잘못된 매핑·누락 CASE 를 넣으면 검증이 실패하는 것"이다 (개발프롬프트). REQ-SFR-066-001 은 conflict fixture, REQ-SFR-038-001 은 화면 + 비UI 분할 fixture 로 고정한다 (`fixtures/conflicts/`).
- 검증 결과는 네 값을 유지하고 실행 오류·미설치를 성공으로 표시하지 않는다 (설계 §10). 검토 데이터가 없어 건너뛴 테스트는 skipped 이지 pass 가 아니다 (`data/review/README.md`).
- 세 상태 체계(작업/산출물/검증)를 합치지 않는지 테스트로 고정한다 (`packages/schemas/src/status-enums.test.ts`).

## 7. 용어

| 용어 | 정의 | 출처 |
|---|---|---|
| 내부 UUID | 시스템이 부여하는 불변 식별자. Requirement, ScreenPlan, 화면 요소에 각각 두며 외부 ID·표시 번호와 분리한다 | 설계 §6, §9 |
| 외부 화면 ID (기존 화면 ID) | 사용자에게 익숙한 S2B 파일명 기반 화면 식별자. INDEX 의 `id`. 프로젝트 내 현재 값은 유일하며 SP 번호로 강제 교체하지 않는다 | 설계 §6 |
| 외부 REQ ID | 요구사항 원장 SFR 시트 지정 열의 `REQ-SFR-NNN-NNN`. 내부 UUID 와 별도 저장 | 설계 §6; 보고서 §3 |
| 표시 번호 (a/b/c) | 화면·설명에 표시되는 영역 내 요소 번호. 영역마다 반복 가능하며 내부 요소 UUID 와 구분 | 설계 §9 |
| 별칭 이력 | 화면 ID·파일명 변경 시 이전 ID 를 남기는 기록. 이름 하나로 자동 생성하지 않는다 | 설계 §6; 보고서 §4 |
| 경로 이동 기록 | 파일명·경로 변경 시 별칭 이력과 함께 남기는 명시적 변경 작업의 기록 | 설계 §6 |
| 임시 레코드 | 중복 수입된 화면 ID·경로를 해결 전까지 공식 레지스트리와 분리해 보관하는 레코드 | 설계 §6 |
| 기준 버전 (baseline) | 채택한 자료·요구사항·정책·화면·템플릿의 정확한 버전 묶음. 생성 작업이 고정하는 기준 | 설계 §6, §8, §9 |
| 검토 필요 | 생성 작업 완료 시 고정한 기준 버전이 최신 기준과 달라진 경우의 표시 | 설계 §6 |
| stale | 요구사항·정책 변경으로 기존 승인 산출물이 더 이상 최신이 아님을 나타내는 산출물 상태 | 설계 §11 |
| 작업 상태 | queued → running → succeeded / failed / cancelled. 산출물 승인 상태와 독립 | 설계 §11 |
| 산출물 상태 | draft → validation_pending → review_ready → approved; 변경 시 새 draft 또는 stale | 설계 §11 |
| idempotency key | GenerationJob 의 중복 실행 방지 키. 입력 버전·진행 단계·제한 시간·취소 요청과 함께 둔다 | 설계 §11 |
| revision | 편집 가능한 레코드의 개정 번호. 동시 편집 충돌 검사와 PATCH 의 필수 값 | 설계 §11, §13 |

| StateModel | 적용 범위·값·전이·예외·근거를 가진 업무 상태 체계. 출처 체계마다 별도 레코드 | 설계 §6; 보고서 §4 |
