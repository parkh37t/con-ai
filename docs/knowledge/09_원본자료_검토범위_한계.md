# 09. 원본 자료 13개의 정체·역할·검토 범위와 한계

검토 패키지가 원본 13개에 대해 **무엇을 확인했고 무엇을 확인하지 않았는지**를 파일 단위로 정리하고, 개발에서 원본을 어떻게 취급해야 하는지를 규칙으로 고정한다. 출처 범위: 보고서 전체(§검토 범위, §1~§7), 설계 §1·§3·§4·§5·§6·§7·§8·§10·§12·§13·§14·§15, 개발프롬프트, `data/review/README.md`, 검토 데이터 실측(`원본파일_인벤토리.json`, `MD_검토목록129건.csv`, `집계기준_결과.json`, CSV 4종). 원본은 `docs/reference/`에 있으며 이 문서는 요약·해석이다.

## 1. 한 문장 요약

검토 패키지는 CON-AI 폴더의 원본 13개(HTML 3, ZIP 2, PPTX 6, XLSX 1, TXT 1; 합계 172,516,866바이트)를 hash로 식별하고 S2B2.zip(2,280엔트리)·apex ZIP(35엔트리)의 구조를 추출했으나, **1,603개 HTML의 동작 검증, 444개 요구사항의 수용조건 판정, 129개 MD 정책의 정오 검증은 하지 않았다** (보고서 §검토 범위). 각 원본은 역할이 다르다: BNK 3파일은 생성 작업대 UX 참고(성공 표시는 실제 검증이 아님), S2B2.zip은 업무 자료·규격·레지스트리 원천(INDEX 등록≠구현 완료, REQ 토큰≠승인 매핑), APEX는 단계별 계약·검토 개념(12역할 전면 도입 유보), Design_AI_Process는 구조 고정→디자인 계약, PPT 4종은 장기 방향·제품화 근거(수치는 주장), 테스트 계획·카카오톡은 파일럿 과제와 변경요청 기능의 근거다 (보고서 §1, §6). 보고서 §3 표와 `집계기준_결과.json`의 수치는 동봉 CSV/JSON 실측과 전부 일치했다. 다만 보고서가 적은 HTML 외부참조 1,551개, 정규식 526건, BNK 471~505행, 테스트 계획 13과제/7완료 등은 동봉 데이터로 재현할 수 없어 **문서 진술**로만 남는다.

### 2.4 BNK: 재사용할 UX와 새로 구현할 기능 (보고서 §2)

| 재사용할 부분 (UX) | 새로 구현할 부분 (기능) |
|---|---|
| 대상 선택 | 모델 호출 |
| 변경 목적·유지 조건 | 결과 저장 |
| 문맥 표시 | 실제 검증 |
| 참고 화면 | 수정 이력 |
| CASE·기기 미리보기 | 버전 충돌 |
| 다운로드 | 승인과 실패 처리 |

- 미리 저장한 HTML을 표시하는 데모와 사용자 프롬프트로 새 결과를 만드는 기능을 수용 테스트에서 구분한다 (보고서 §2 35행).
- 재사용 범위는 설계 §3의 다섯 작업 유형(단건 수정, 신규 생성, 페이지→팝업, 참조 복제, 구조적 재생성)이며 MVP는 신규·단건 수정·참조 복제를 먼저 구현한다 (설계 §3 52행).
- BNK 데모의 모델 선택지 이름은 실제 서비스 지원 모델로 채택하지 않는다 (설계 §8 170행). BNK의 타이머 기반 성공 표시는 운영 검증에 사용하지 않는다 (설계 §10 224행).

### 5.4 코드 초안과의 차이

코드는 고치지 않고 차이만 적는다.

| 항목 | 코드 초안 (커밋됨) | 이 관점의 함의 | 처리 |
|---|---|---|---|
| `SourceType` | `packages/schemas/src/source.ts` 12행: `xlsx / md / csv / html / index` (설계 §4 MVP 입력 형식) | 원본 13개 중 PPTX 6·ZIP 2·TXT 1은 이 enum으로 SourceDocument 등록이 불가하다 | 제안: `pptx`, `zip`, `txt`(또는 `other`) 추가 여부를 ADR로 결정. 설계 §4는 "범용 ZIP 이관"을 후속으로 두므로 ZIP은 "참고 보관"용 유형으로만 |
| SourceDocument 역할 | `note` 자유 문자열만 있음 (source.ts 22행) | §5.1의 역할 분류(ux_reference 등)를 담을 필드가 없다 | 제안: `role` enum 추가 또는 `note` 규약. ADR 필요 |
| SourceVersion | `sha256` 필수, `size_bytes` 선택 (source.ts 32·35행) | 인벤토리 13항목은 bytes·sha256을 모두 갖고 있어 시드 가능. fixtures README가 적은 대로 원본 없이는 합성 버전 레코드를 만들 수 없다 | 일치. 백업 PPTX의 `same_text_different_hash` 관계 필드는 없음(제안) |
| `ScreenRegistryStatus` | `registered / import_candidate / duplicate_id / path_resolution_required` (screen.ts 87~89행) | §5.2의 `candidate_conflict`(후보가 기등록 href)와 duplicate의 같은 href/다른 href 구분이 없다 | 제안. 사이드카 또는 enum 확장은 ADR로 |
| `TraceLinkStatus` | `candidate / approved / conflict / excluded / non_ui` (trace-link.ts 17행) | `unknown_requirement`(원장 부재 122행), `unregistered_artifact`(INDEX 미등록 90개)를 표현할 값이 없다 | 제안. 후보 수입 시 `candidate` + 사유 필드로 우회 가능 |
| `XlsxImportConfig` | sheet·header_row·id_column·id_pattern (import-config.ts) | R7과 일치. XLSX 수입기 본체는 아직 없음(`packages/importers`에는 `csv.ts`와 `review-data.test.ts`만) | 일치 |
| `review-data.test.ts` | CSV 5종을 `집계기준_결과.json`과 대조, 부재 시 `describe.skipIf`로 skipped (19~27행) | R29와 일치. 인벤토리 JSON(13항목·바이트 합·슬라이드 수)과 README 해시 표는 검사하지 않는다 | 제안: 인벤토리·해시 대조 테스트 추가 |
| `ValidationStatus` | `pass / fail / error / not_run` (validation.ts) | R16·R34와 일치 | 일치 |
| fixtures | `req-sfr-066-001.conflict.json`, `req-sfr-038-001.non-ui-split.json`, `registry/duplicate-id.sample.json`, `registry/missing-path.sample.json` | §5.2 충돌 fixture 중 "쿼리스트링 href", "기등록 후보", "원장 부재 토큰(`SFR-xxx`)" 예제는 없다 | 제안: 합성 ID로 추가 (인용 경로 수를 늘리지 않음) |
| `ChangeRequest` | 스키마 없음 (schemas README "남은 제한") | §5.1 ChangeRequest 분류값·필수 필드 | 후속 |
| 루트 README | `docs/knowledge`·`docs/decisions`·`docs/plan`·`CLAUDE.md`를 완료로 표기 | 이 문서 작성 시점에 해당 디렉터리를 만드는 중 | 문서 작성 완료 후 README 상태 문구 갱신 필요 |
