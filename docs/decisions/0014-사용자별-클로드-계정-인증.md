# 0014. 사용자별 Claude 계정 인증 — 각자 자기 토큰으로 쓰기

상태: 제안(1단계는 채택, 2단계는 확인 필요) · 2026-09-05

## 배경

이 제품은 URL 로 접속하는 팀용 워크스페이스다. 기획자·디자이너·퍼블리셔가 각각 브라우저로 들어와 화면을 생성하고 검토한다. 모델 호출 비용과 사용량을 **서버 한 개의 공용 키**로 부담하면 다음 문제가 생긴다.

- 누가 얼마나 썼는지 분리되지 않는다(비용 배분·한도 관리 불가).
- 공용 키 하나가 유출되면 전원이 영향을 받는다.
- 개인이 이미 가진 Claude 구독·크레딧을 쓸 수 없다.

사용자 요구: **각자 자기 Claude 계정으로 로그인해 자기 토큰을 쓴다.**

## 결정

인증을 두 단계로 나눈다. 1단계는 지금 구현하고, 2단계는 Anthropic 의 서드파티 OAuth 등록 조건을 확인한 뒤 어댑터만 교체한다.

### 1단계 — 사용자별 자격 증명 보관 (BYOK, 채택)

| 항목 | 설계 |
|---|---|
| 로그인 | 워크스페이스 자체 로그인(이메일 + 초대). 세션은 HttpOnly·SameSite=Lax 쿠키 |
| 자격 증명 등록 | 설정 화면에서 본인 **API 키**(`sk-ant-…`) 또는 **토큰**(Bearer)을 붙여넣는다 |
| 저장 | 서버에서 봉인(`AES-256-GCM`, 키는 서버 환경변수 `CON_AI_SECRET`). 평문은 DB·로그·응답 어디에도 남기지 않는다 |
| 표시 | 화면에는 방식(`API 키`/`토큰`)과 끝 4자리만. 원문 재조회 API 없음 |
| 사용 | 생성 작업은 **요청한 사용자의 자격 증명으로** 어댑터를 만들어 실행한다. 작업 레코드에 `requested_by`, `auth_kind`, `usage` 기록 |
| 없을 때 | 서버 기본 자격 증명이 있으면 그것으로(관리자가 켠 경우), 없으면 fixture 더미 어댑터로 실행하고 화면에 명시 |
| 폐기 | 사용자가 언제든 삭제. 삭제 시 진행 중 작업은 계속, 새 작업은 기본값으로 |

### 2단계 — Claude 계정 OAuth (확인 필요)

브라우저에서 "Claude 계정으로 로그인" → 동의 → 서버가 authorization code 를 access/refresh 토큰으로 교환 → 사용자별 토큰을 1단계와 같은 방식으로 봉인 저장 → 만료 전 자동 갱신.

SDK 는 이 형태를 이미 지원한다(확인함): `new Anthropic({ credentials: <AccessTokenProvider> })` 로 토큰 공급자를 넘기면 요청마다 `Authorization: Bearer` 를 붙이고 토큰 캐시·갱신을 처리한다. `authToken` 직접 지정 경로와 달리 만료 갱신이 내장된다.

**확인해야 할 것** — 이 개발 환경은 외부 문서·콘솔 접근이 프록시에 막혀 검증하지 못했다.
1. Anthropic 이 서드파티 앱의 OAuth 클라이언트 등록을 제공하는지, 제공한다면 신청 경로와 승인 조건.
2. 발급 토큰의 스코프와 요금 청구 주체(개인 구독 vs 조직 API 크레딧).
3. 개인 Claude 구독 토큰으로 Messages API 를 호출하는 것이 이용약관상 허용되는지. **허용되지 않으면 2단계는 폐기하고 1단계(개인 API 키)만 유지한다.**

확인 전까지 2단계를 구현하지 않는다. 추측으로 OAuth 엔드포인트를 만들지 않는다.

## 근거

- 설계 §5 "모델 키는 서버에 저장한다" — 사용자별로 나뉘어도 서버 보관 원칙은 그대로다. 브라우저에는 어떤 자격 증명도 내려보내지 않는다.
- 설계 §5 "생성 HTML 은 격리해 표시하며 모델 키·사용자 인증정보를 전달하지 않는다" — iframe 미리보기와 자격 증명 경로를 분리한다.
- 설계 §2 "승인자·대상 버전·승인 시점은 남긴다" — 작업 실행자도 같은 수준으로 남긴다.

## 영향·대안

- **대안 A: 서버 공용 키 하나** — 지금 상태. 팀 파일럿에는 충분하나 비용 분리·유출 범위 문제가 남는다. 1단계 도입 후에도 관리자 기본값으로 유지할 수 있다.
- **대안 B: 브라우저에 키 저장(localStorage)** — 채택하지 않는다. 생성·검증은 서버에서 하므로 키가 브라우저를 거칠 이유가 없고, XSS 한 번에 유출된다.
- 다중 사용자 인증이 들어오면 승인자·코멘트 작성자의 "이름 문자열"이 실제 계정으로 바뀐다. 기존 데이터는 문자열로 남는다(마이그레이션 시 별도 기록).

## 되돌릴 조건

개인 자격 증명 사용이 약관상 문제가 되거나, 팀이 단일 조직 키 정산을 선호하면 1단계를 끄고 서버 기본 자격 증명만 사용한다. 저장 구조는 그대로 두고 사용 지점만 바꾼다.
